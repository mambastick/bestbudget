# BestBudget Implementation Plan

## Цель ближайшего этапа

Перевести BestBudget из прототипа в цельное Vite + React приложение с корневой
структурой `src/`, shadcn/ui как основной дизайн-системой, локальной
пользовательской моделью, рабочими пространствами, валютами, категориями,
календарем и раздельными dev/prod сценариями контейнеризации.

## 1. Структура проекта

### Требование

Проект не должен быть разделен на `frontend/` и `backend/`, пока приложение
работает как web-first SPA без отдельного серверного API.

### Критерии готовности

- Исходный код приложения находится в корневой директории `src/`.
- Vite-конфигурация, `components.json`, `index.html`, `tsconfig*` и
  `eslint.config.js` находятся в корне репозитория.
- Корневые команды `pnpm dev`, `pnpm build`, `pnpm lint`, `pnpm typecheck`
  работают без package filters.
- Удалены устаревшие ссылки на `frontend/`, `backend/` и `@bestbudget/backend`.

## 2. Аутентификация

### Требование

Стартовый экран должен поддерживать два режима: регистрация нового аккаунта и
вход в существующий аккаунт. Данные пользователя должны быть привязаны к
учетной записи, а не к единственной глобальной браузерной сессии.

### Критерии готовности

- Регистрация требует имя, email и пароль.
- Вход требует email и пароль.
- Пользовательские данные сохраняются в локальное хранилище с разделением по
  `userId`.
- При повторном входе пользователь видит свои пространства, категории,
  операции, бюджеты, документы и календарные события.
- Ошибки регистрации и входа показываются через toast.

## 3. Аккаунт и меню пользователя

### Требование

Клик по аккаунту в сайдбаре не должен автоматически переводить в настройки.
Должно открываться меню пользователя с действиями аккаунта.

### Критерии готовности

- В нижней части сайдбара отображается аватар, имя и email текущего пользователя.
- По клику открывается `DropdownMenu`.
- В меню есть переход в настройки аккаунта и отдельное действие выхода.
- Выход визуально выделен как destructive action.

## 4. Пространства

### Требование

Верхняя зона выбора `BestBudget` должна использоваться для переключения
рабочего пространства. Пользователь может вести несколько пространств.
Разделение на "личное" и "семейное" заменяется на модель доступа:
индивидуальное пространство или совместное пространство.

### Критерии готовности

- Пользователь может создать несколько пространств.
- В шапке/брендовой зоне можно выбрать активное пространство.
- У пространства есть название, валюта, владелец и участники.
- Тип пространства хранится как `individual` или `shared`.
- Все операции, бюджеты, категории, документы и обязательства привязаны к
  активному пространству.

## 5. Валюты

### Требование

Валюта не вводится вручную как строка. Пользователь выбирает валюту из
подготовленного справочника.

### Критерии готовности

- Валюта выбирается через `Select`.
- В списке отображаются ISO-код, символ валюты, страна/регион через emoji и
  понятное название: например `🇷🇺 RUB ₽ Российский рубль`.
- В приложении используются символ и ISO-код выбранной валюты.
- Минимальный справочник включает RUB, USD, EUR, AED, UAH, KZT, GEL, AMD, TRY.

## 6. Категории

### Требование

Категории должны быть шаблонами, а не свободным текстовым полем. Пользователь
выбирает из преднастроенного списка и может добавить собственные категории.

### Критерии готовности

- Есть преднастроенные категории: еда, ЖКХ, транспорт, развлечения, здоровье,
  связь, подписки, образование, дом, доход, кредиты, накопления.
- При создании операции и бюджета категория выбирается из списка.
- Пользователь может создать пользовательскую категорию.
- Пользовательская категория сохраняется в активном пространстве.

## 7. Дизайн

### Требование

Вернуть более стандартный shadcn/ui визуальный язык с синим primary-цветом.
Fluent/Mica-эксперимент должен быть убран из основной UI-системы.

### Критерии готовности

- Основные поверхности реализованы через shadcn `Card`, `Sidebar`, `Table`,
  `Dialog`, `Sheet`, `Select`, `DropdownMenu`, `Tabs`, `Calendar`.
- Primary-цвет возвращен к синему shadcn/Cupertino-подобному тону.
- Убраны кастомные `fluent-*` классы из основной компоновки.
- Нет горизонтального overflow на мобильных экранах.

## 8. React Bits анимации

### Требование

Интерфейс должен выглядеть живее за счет аккуратных React Bits-style анимаций,
но критичные финансовые формы не должны зависеть от декоративных эффектов.

### Критерии готовности

- Используются отдельные компоненты анимаций в `src/components/reactbits/`.
- Анимации применяются к входному экрану, появлению карточек, спискам и
  hover-состояниям.
- Анимации учитывают `prefers-reduced-motion`.
- Анимации не ломают доступность и не мешают работе форм.

## 9. Календарь

### Требование

Календарь должен быть первоклассным рабочим экраном, а не маленьким виджетом.

### Критерии готовности

- Есть месячный календарь с выбранной датой.
- Дни с событиями визуально помечаются.
- Справа отображается список операций, платежей и обязательств на выбранную
  дату.
- Можно создать операцию или платеж из календарного экрана.
- День календаря обновляет правую панель без перезагрузки.

## 10. Настройки семьи / пространства

### Требование

Настройки совместного пространства должны показываться карточкой: в хедере
название пространства, ниже список участников, последним элементом пунктирная
карточка приглашения.

### Критерии готовности

- Карточка пространства показывает название, валюту и список участников.
- Участники отображаются с аватаром, email и ролью.
- Приглашение нового пользователя открывается по клику на пунктирную карточку
  `+ Пригласить`.
- Приглашенный участник появляется в списке со статусом `invited`.

## 11. Deploy

### Требование

`deploy/` должен быть разделен на `dev/` и `prod/`.

### Критерии готовности

- `deploy/dev/` собирает локальный dev-контейнер.
- Dev-контейнер монтирует код репозитория внутрь контейнера, чтобы локальные
  изменения были видны через Vite HMR.
- Пользовательский запуск приложения выполняется только через Docker; прямой
  запуск `pnpm dev` не документируется и не используется как основной сценарий.
- `deploy/prod/` запускает приложение из образа, который pull-ится из registry.
- Production Dockerfile собирает статический Vite build и отдает его через nginx.
- В README описаны обе команды запуска.

## Последовательность выполнения

1. Завершить перенос проекта в корень.
2. Обновить package scripts, tsconfig, Vite, MCP и README.
3. Разделить `deploy/dev` и `deploy/prod`.
4. Разбить монолитный `App.tsx` на доменные и UI-модули.
5. Реализовать локальную auth-модель.
6. Реализовать пространства, валюты и категории.
7. Пересобрать экраны: overview, операции, бюджеты, календарь, семья, настройки.
8. Добавить React Bits-style анимации.
9. Прогнать `typecheck`, `lint`, `build` и smoke-test.
10. Сделать commit и push.
