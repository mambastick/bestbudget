# Локализация BestBudget

Фаза 1 добавляет ru/en без префиксов URL, переводы каркаса, auth/onboarding, настроек и ошибок. Финансовые экраны и фоновые уведомления переводятся в фазе 2. Сохранённые пользователями названия, заметки и старые категории не переводятся и не переименовываются.

## Локаль и предпочтения

`src/i18n/request.ts` — единственная конфигурация next-intl. Порядок: явное `users.locale` (`ru`/`en`) → cookie `bb_locale` → поддерживаемый язык из `Accept-Language` с наибольшим q (при равенстве — первый) → `en`. Региональные варианты сводятся к базовому языку. q=0, некорректные веса и неподдерживаемые языки пропускаются.

`users.locale = null` означает системный язык. Для фоновых сообщений используется явный `users.locale` → `users.last_seen_locale` → `en`. Последняя известная локаль браузера сохраняется при создании аккаунта, входе (включая OIDC), загрузке приложения авторизованным пользователем и смене языковой настройки; она не фиксирует язык интерфейса и не заменяет определение из текущего запроса. Миграция `0009_recipient_last_seen_locale` заполняет `last_seen_locale = ru` только существующим профилям без явного языка; новые пользователи получают язык браузера при регистрации. Повторное определение того же языка не обновляет строку профиля. Выбор «Как в системе» очищает cookie. `setLocaleAction` валидирует выбор, обновляет только пользователя текущей сессии, пишет HTTP-only cookie и инвалидирует layout; клиент делает `router.refresh()`. Запрос читает предпочтение из БД, поэтому смена видна сразу, без ожидания обновления сессии Better Auth. При создании аккаунта переносится явный выбор из cookie; при входе (включая OIDC) сохранённый выбор синхронизируется в cookie. Значение без явного выбора определяется заново из заголовка запроса, а не фиксируется навсегда.

`<html lang>` и metadata формируются на сервере. `NextIntlClientProvider` получает ту же конфигурацию: нет определения языка в `useEffect` и первого кадра с запасным языком. Manifest динамический и зависит от того же запроса. После смены языка уже установленное приложение может сохранить старое название до обновления manifest браузером.

Тема хранится на устройстве стандартным `next-themes` (`theme` в localStorage): `system`, `light`, `dark`. `defaultTheme="system"`, `enableSystem`, предварительный скрипт next-themes и `suppressHydrationWarning` на html сохранены. Отметка в меню использует выбранный режим, а не вычисленный light/dark. До гидратации radio показывает системный режим; цвет страницы устанавливается предварительным скриптом. Для двух меню с выбором предпочтений используется `DropdownMenu animated={false}`: обычный Base UI popup устраняет позднюю передачу фокуса анимированной обёртки при открытии подменю. Открытие клавиатурой и radio-семантика проверяются e2e.

## Словари и ключи

Один файл на область: `messages/{ru,en}/{namespace}.json`. Загрузчик `src/i18n/messages.ts` явно импортирует namespace, чтобы Next.js включал их в standalone. Добавляя область, добавьте **оба** файла и импорт в загрузчик. Не создавайте пустые области заранее.

Ключ описывает смысл и остаётся неизменным при редактуре текста: `category.inUse`, `preferences.systemLanguage`, `login.signIn`. Внутри namespace можно группировать по экрану/компоненту. Строки исходного языка и числовые порядковые номера не подходят для ключей. Код, идентификаторы и комментарии остаются английскими.

```tsx
// Client Component
const t = useTranslations("auth")
const locale = useLocale()
return <Button>{t("login.signIn")}</Button>
```

```tsx
// Async Server Component / metadata
const t = await getTranslations("settings")
const locale = await getLocale()
```

Hooks вызываются только в компонентах/hooks. В чистые функции передавайте `locale` или `t` аргументом. Не держите переведённые подписи в константах уровня модуля: они должны пересчитываться при смене локали. Состояние форм хранит значения/коды, а не словарь опций. Текст с переменными переводится целиком, а не собирается из переводимых фрагментов; для выделения частей используйте `t.rich` и именованные теги. Не вставляйте произвольный HTML из сообщений.

Количество выражайте ICU, с **one/few/many/other** для ru и one/other для en:

```json
{
  "ru": "{count, plural, one {# операция} few {# операции} many {# операций} other {# операции}}",
  "en": "{count, plural, one {# transaction} other {# transactions}}"
}
```

`src/lib/plural.ts` теперь принимает локаль и форму `other` через `Intl.PluralRules`; это переходный API для старых экранов. Новые переводы должны использовать ICU, включая всю фразу и нужный падеж. Пример в поставляемых словарях — `errors.import.undoBlocked`.

## Деньги, числа и даты

Деньги по-прежнему целые минорные единицы. Не меняйте вычисления/хранение ради локализации. `Intl` используется только для представления; парсер строит целое значение из целой/дробной частей и проверяет `Number.isSafeInteger`.

```ts
formatMoney(amount, currency, { locale, sign: true })
formatMoneyCompact(amount, currency, locale)
formatMoneyShort(amount, currency, locale)
minorToInput(amount, currency, locale)
formatDateFull(date, locale)
formatDay(date, locale)
formatDayShort(date, locale)
formatMonth(date, locale)
formatWeekday(date, locale)
formatDateTime(timestamp, householdTimezone, locale)
formatRelativeDay(date, today, locale)
new Intl.NumberFormat(locale).format(count)
```

В клиенте берите `locale` из `useLocale()`, на сервере — из `getLocale()`. В сервис/домен передавайте локаль из вызывающего слоя: фоновые задания не имеют HTTP-запроса. Старые вызовы пока сохраняют default `ru` для совместимости; **при переводе каждой области фазы 2 замените все вызовы форматирования на явную активную локаль**, включая графики, подписи осей, всплывающие подсказки, сортировку и относительные даты. Не передавайте функцию форматирования напрямую в callback с индексом: `tickFormatter={(date) => formatMonth(date, locale)}`.

ISO-даты остаются `YYYY-MM-DD`. Форматирование календарных дат использует UTC, «сегодня» — часовой пояс семьи (`todayIn`), независимо от языка браузера. Календарь `DateField` переключает также подписи и aria-labels react-day-picker. Валютный символ получается из Intl, включая `MoneyInput` и `CurrencySelect`.

### Ввод сумм

`MoneyInput` группирует тысячи тонким пробелом U+2009 в обоих языках; десятичный знак — запятая в ru, точка в en. Парсер принимает оба знака независимо от языка:

- Только один вид разделителя — десятичный: `1234,56` и `1234.56` равны. `1,234` для RUB отклоняется как три десятичных знака, для BHD означает 1.234 BHD. Не угадываем, что это тысячи.
- Есть оба вида — последний знак десятичный, другой обязан группировать строго по три цифры: `1,234.56` и `1.234,56` равны; `12,34.56` отклоняется.
- Пробелы, NBSP, тонкий и узкий неразрывный пробел допустимы как группировка; знак ₽ поддерживается для совместимости.
- Отрицательные значения, экспоненциальная запись, лишние разделители, дробь для JPY и небезопасные целые отклоняются. При вводе поле ограничивает дробную часть экспонентой валюты, как раньше; для полноценной проверки используйте `parseMoney`, а не только нормализатор поля.

## Ошибки и Zod

`AppError` принимает **типизированный ключ** из `errors`, параметры и, при необходимости, категорию ошибки:

```ts
throw new AppError("category.inUse")
throw new AppError("import.loanPayment", { rowLocator: row.rowLocator })
throw new AppError("session.expired", {}, "unauthorized")
```

Используйте существующие ключи/`forbidden()`, `notFound()`, `conflict()` прежде чем добавлять новый. Ключи имеют смысл; не используйте текст исключения от провайдера/SQL как ключ или параметр. `messageKey` и `params` хранят структуру, `code` сохраняет категорию доступа/конфликта. `Error.message` оставляет русский диагностический текст для совместимости прямых вызовов сервисов; **HTTP-ответы** локализует `runAction` через `getLocale()`. Контракт `ActionResult` не меняется: `{ok:false,error,fieldErrors?}`. Не показывайте клиенту `err.message` напрямую.

Схемы Zod могут хранить ключ (`.min(1, "validation.titleRequired")`). `runAction` преобразует каждую issue в активную локаль и сохраняет пути полей. Стандартные issue используют локальную error map Zod; `invalid_type` имеет нейтральный перевод без вывода входного значения. Не вызывайте глобальный `z.config(locale)`: параллельные запросы могут иметь разные языки. Вне server action используйте `zodIssueMessage(issue, locale)` на границе выдачи ответа. Не меняйте схему глобально ради текущего пользователя.

Неизвестные исключения скрываются за переводом `unexpected`; в логах остаются только имя ошибки и SQLSTATE. Better Auth отображается через `authErrorMessage(error, locale)` с переводом по известному коду и безопасным запасным сообщением. Письмо сброса пароля использует локаль получателя, независимо от cookie и заголовков инициатора. Отправщик приглашений выбирает локаль известного адресата, а для неизвестного — отправителя; интерфейс приглашений пока выдаёт только ссылку.

Категории и основной счёт создаёт `householdDefaults(locale)` в `src/domain/defaults.ts`. Локаль приходит из `createHouseholdAction`. Это имена данных на момент создания; смена языка интерфейса не должна менять существующие записи.

## Проверки и расширение фазы 2

`npx -y pnpm@10.27.0 i18n:check` включён в CI `checks`. Скрипт сравнивает листовые ключи всех namespace ru/en, проверяет TS AST в полностью переведённых путях из `scripts/i18n.config.ts` и предупреждает о потенциально неиспользуемых ключах. Комментарии, тесты и fixtures не сканируются. Исключение для строкового литерала `Русский` — название языка на нём самом. Не расширяйте исключения для обхода незавершённого перевода.

Проверка неиспользуемых ключей консервативна: динамические обращения и передаваемые функции-переводчики требуют ручного просмотра. Предупреждение не является разрешением удалять ключ. Добавьте полностью переведённую область в `translatedPaths` **в том же PR**, затем запустите `typecheck`, `lint`, `test`, `i18n:check`, `build` и релевантный e2e. Экраны проверяйте на ru/en, desktop/375px, light/dark; пользовательские названия могут оставаться русскими в английском UI.

Vitest фиксирует `Date` перед каждым тестом через `tests/setup-env.ts`; общий момент времени задан в `tests/clock.ts` переменной `TEST_NOW`. Для сценариев, зависящих от текущего дня, используйте `testNow` и производные ISO-даты, не реальное время и не отдельные часы в fixture hooks. Чистые проверки форматирования могут передавать явную дату. CI запускает весь набор на трёх значениях `TEST_NOW` из `.github/workflows/ci.yml` (обычный день, начало месяца и конец года); новые тесты должны проходить на всех трёх.

`e2e/i18n.spec.ts` работает на изолированной production-сборке и БД (3200/54330). Создаёт отдельного синтетического пользователя; проверяет английский браузер, cookie до входа, сохранение языка в меню и профиле, manifest, тему после reload и реакцию system на эмуляцию `prefers-color-scheme`. Скриншоты создаются в `docs/screenshots/i18n/`. Русская acceptance-конфигурация задаёт `ru-RU`; явно создаваемые `browser.newContext()` тоже должны задавать её.

## Новый язык

1. Добавьте код в `LOCALES`, `isLocale`, определение языка браузера и предпочтения UI.
2. Расширьте enum в `users.locale`/Better Auth и при необходимости ограничение БД; создайте новую аддитивную миграцию, не меняйте старые.
3. Добавьте полные namespace и импорт в загрузчик; включите новый язык в `i18n:check`, `errorTranslator`, Zod error map, default category names, `DateField` и краткие денежные суффиксы.
4. Проверьте все формы ICU для нового языка, валюты, даты, ввод сумм и fallback. Добавьте unit/integration/e2e; проверьте standalone build и manifest.
