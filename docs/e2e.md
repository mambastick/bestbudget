# Матричные e2e-проверки

`npx -y pnpm@10.27.0 test:e2e` собирает production-приложение и запускает standalone-сервер с отдельной PGlite на портах 3200/54330. Каждый запуск начинает с пустой БД. Процессы приложения владельца на 3000/3100/54329 не используются.

В `assets-i18n`, `finance-i18n` и `admin-i18n` каждый вариант ru/en × light/dark × 1280/375 — отдельный тест с лимитом 60 секунд. Seed создаётся в `beforeAll` один раз на спек; подготовительный браузер дожидается завершения запросов и закрывается перед seed CLI, авторизация переиспользуется через cookies, браузерный контекст создаётся заново для каждого теста. Проверки переполнения, гидрации и консольных ошибок выполняются в каждом варианте. Сценарии изменения финансовых данных вынесены в отдельные тесты после матрицы.

При падении Playwright перезапускает worker и выполняет `beforeAll` заново: случайный e-mail создаёт нового пользователя и семью. Следующие варианты не зависят от успешного завершения предыдущего. В административной спеке заменяется только тестовая запись доставки с её собственным dedupe key, поскольку список доставок общий для всей установки.

Service Worker в трёх матрицах отключён: его установка в каждом новом контексте не относится к проверкам финансовых экранов и отдельно покрывается PWA-спекой.

В PWA отдельно параметризованы Safari/Chrome и light/dark standalone; `imports` уже состоит из отдельных сценариев и большой матрицы не содержит.

Один worker сохранён по результатам проверки, а не только из-за общих данных. Эксперимент с двумя workers для трёх изолированных матриц после завершения глобальных сценариев упал при seed с SQLSTATE `08P01`: `bind message supplies … parameters, but prepared statement "" requires …`. PGlite — односессионная БД; socket-сервер мультиплексирует клиентов, но не обеспечивает полную семантику независимых PostgreSQL-сессий. Уникальных пользователей и семей недостаточно. Кроме того, acceptance меняет глобальные настройки OIDC и временно блокирует остальных администраторов, а PWA-проверка обновления подменяет общий `sw.js` production-сервера. Для двух workers нужны полноценный PostgreSQL с отдельными сессиями и изоляция глобальных сценариев либо отдельные сервер/БД на worker. Новые `ai-*` спеки не менялись.

Скриншоты матриц, локализации, существующей AI-спеки и PWA (включая `public/screenshots`) обновляются только вручную:

```bash
UPDATE_SCREENSHOTS=1 npx -y pnpm@10.27.0 test:e2e
```

В существующей AI-спеке локаторы ограничены видимым активным чатом, а в acceptance — видимой карточкой прогноза: скрытые Activity-деревья предыдущего маршрута не участвуют в проверках. Скриншоты больше не служат случайной паузой между действиями. Новые `ai-*` спеки в эту правку не входят.

В обычном прогоне нет безусловной записи снимков каждой страницы матрицы. Диагностика Playwright и JSON-вложение finance остаются в `work/playwright`; после неуспешного теста сохраняется trace с DOM-снимками, консолью и сетью. Покадровый скринкаст trace отключён, чтобы не кодировать кадры во время каждого успешного прогона; проверки UI и явные снимки с `UPDATE_SCREENSHOTS=1` от него не зависят. `E2E_SKIP_BUILD=1` позволяет переиспользовать существующую production-сборку; для сравнения времени нужно одинаковое значение этого параметра до и после.

## Параллельная работа агентов на одном Linux-хосте

Ожидание свободных портов не предотвращает одновременный старт двух Playwright-процессов. Для локальной проверки можно использовать отдельный user/network namespace: внутри остаются те же 3200/54330, а тесты других worktree не могут подключиться к этим серверу и БД. Это не требование CI. Зависимости и Chromium должны быть заранее установлены; `npm` внутри namespace использует локальный кэш.

```bash
mkdir -p /var/tmp/codex-golodn1y/bestbudget-e2e
TMPDIR=/var/tmp/codex-golodn1y/bestbudget-e2e \
  unshare --user --map-root-user --net \
  sh -c 'ip link set lo up && npm_config_offline=true npx -y pnpm@10.27.0 test:e2e'
```

Для сравнения времени используется исходный `main` и три полных прогона после изменения в одинаковом namespace/ENV, с новой PGlite и `next build` каждый раз. Неуспешные и конфликтные старты не включаются в сравнение успешных полных прогонов, но указываются отдельно. Подробные результаты и ссылки на CI — в [PR #35](https://github.com/mambastick/bestbudget/pull/35).
