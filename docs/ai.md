# ИИ-ассистент

Фундамент предоставляет чат, настройки, инструменты чтения и подтверждаемые предложения. Фаза 2 добавляет интервью для составления бюджета, входящие рекомендации и периодический разбор по расписанию. Ассистент выключен по умолчанию; без согласия семьи финансовые данные провайдеру не отправляются.

## Включение

1. Системный администратор открывает **Администрирование → ИИ-ассистент**: выбирает провайдера, адрес, модель, при необходимости ключ, температуру и лимит токенов.
2. **Получить модели** запрашивает каталог провайдера. Поле модели остаётся редактируемым: можно ввести идентификатор вручную. Каталог сам по себе не подтверждает поддержку инструментов.
3. **Проверить подключение** выполняет небольшой запрос с принудительным вызовом `connection_check`. Затем сохраните настройки с включённым флагом. При включении проверка выполняется повторно. Модель без tool calling использовать нельзя. Проверка может тарифицироваться провайдером; финансовых данных в ней нет.
4. Владелец семьи открывает **Настройки → Семья → ИИ для семьи**, проверяет провайдера, модель и адрес назначения, выбирает уровень данных, включает ассистента и подтверждает согласие.
5. В навигации и на обзоре появляется **Ассистент**. Можно создать диалог, изучить расходы и применить выбранные пункты карточки.

Системный администратор видит только конфигурацию и статистику токенов по семьям. Само администрирование не даёт доступа к финансовым данным чужой семьи. Доступные в проекте семейные роли — owner/admin/member; ИИ использует существующую матрицу `can(...)`, отдельную роль viewer эта фаза не вводит.

## Конфигурация через ENV

При непустом `AI_PROVIDER` вся конфигурация берётся из ENV, поля в админке доступны только для чтения. Секрет из БД при этом не подмешивается. После изменения ENV перезапустите приложение и выполните **Проверить подключение** в админке. Результат проверки привязан к конфигурации, включая ключ; при смене подключения его нужно проверить заново. `AI_ENABLED=true` без проверки и согласия семьи не открывает API.

| Переменная | Назначение |
|---|---|
| `AI_PROVIDER` | `openai`, `openai_compatible`, `anthropic`, `google`, `gigachat`; пусто — настройки БД |
| `AI_BASE_URL` | HTTP(S) base URL; для совместимых серверов обычно заканчивается на `/v1` |
| `AI_API_KEY` | API key; для GigaChat — ключ авторизации Base64(client_id:client_secret), без префикса `Basic` |
| `AI_MODEL` | Идентификатор модели, без встроенного значения по умолчанию |
| `AI_ENABLED` | `false` по умолчанию; включается только явно |
| `AI_TEMPERATURE` | Необязательно, диапазон 0–2; конкретная модель может ограничивать параметр |
| `AI_MONTHLY_TOKEN_LIMIT` | Целое число, лимит на каждую семью; `0` — без лимита |
| `AI_SELF_HOSTED` | `false`; отметка администратора о размещении модели на своём сервере |
| `AI_GIGACHAT_SCOPE` | `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B`, `GIGACHAT_API_CORP` |
| `AI_GIGACHAT_AUTH_URL` | По умолчанию `https://ngw.devices.sberbank.ru:9443/api/v2/oauth` |
| `NODE_EXTRA_CA_CERTS` | Путь к PEM с дополнительными доверенными CA; применяется Node.js при старте |

Не помещайте ключ в base URL, параметры URL или логи. Ключ из формы хранится зашифрованным через `src/lib/crypto.ts` (AES-256-GCM), в браузер не возвращается. Пустое поле сохраняет ключ, отдельный флаг удаляет его. Сохраните `ENCRYPTION_KEY`/`BETTER_AUTH_SECRET` вместе с защищённой резервной копией.

Compose передаёт переменные приложению; примеры в `.env.example` закомментированы. В Helm используйте `ai.*`, а ключ передавайте через `existingSecret` → `AI_API_KEY` либо защищённый `ai.apiKey`. Пустой `ai.provider` оставляет управление в UI.

## Провайдеры

Имена ниже — примеры настройки, а не список зашитых моделей. Выбирайте модель, доступную вашему аккаунту и поддерживающую инструменты. Реальное подключение каждого платного провайдера требует собственного ключа; автоматические тесты используют mock и не подтверждают доступность конкретного аккаунта, тариф или качество модели.

| Провайдер | Тип | Base URL | Модель / ключ |
|---|---|---|---|
| OpenAI | `openai` | `https://api.openai.com/v1` | Из каталога OpenAI, API key; используется Responses API |
| Anthropic | `anthropic` | `https://api.anthropic.com/v1` | Из Models API, Anthropic API key |
| Gemini | `google` | `https://generativelanguage.googleapis.com/v1beta` | Из каталога Gemini, Google API key |
| OpenRouter | `openai_compatible` | `https://openrouter.ai/api/v1` | Например идентификатор `vendor/model` из каталога, ключ OpenRouter |
| Ollama | `openai_compatible` | `http://ollama:11434/v1` | Установленная tool-capable модель; ключ может быть пустым; каталог `/v1/models`, fallback `/api/tags` |
| LM Studio | `openai_compatible` | `http://host.docker.internal:1234/v1` | Загруженная модель с tool calling; адрес должен быть доступен из контейнера |
| vLLM / LocalAI / llama.cpp server | `openai_compatible` | URL вашего сервера + `/v1` | Имя опубликованной модели; ключ по настройке сервера |
| DeepSeek / Groq / Together / Mistral | `openai_compatible` | OpenAI-compatible base URL из документации выбранного сервиса | Каталог сервиса или ручной ввод; ключ этого сервиса |
| Yandex Cloud AI Studio / YandexGPT | `openai_compatible` | `https://ai.api.cloud.yandex.net/v1` | URI `gpt://<folder_ID>/<model_ID>/latest`, API key сервисного аккаунта с правами на модель |
| GigaChat | `gigachat` | `https://api.giga.chat/v1` | Из `/models`, ключ авторизации и соответствующий scope |

OpenAI-совместимые endpoints различаются поддержкой моделей, схем и учёта токенов. Обязателен успешный тест инструмента; одного текстового ответа недостаточно. Если endpoint не публикует каталог, используйте ручной ввод. Каталоги могут содержать модели без tool calling.

Yandex документирует OpenAI-compatible endpoint и URI моделей в [инструкции интеграции](https://yandex.cloud/en/docs/tutorials/ml-ai/ai-model-ide-integration). Доступность инструментов зависит от модели и API; проверка подключения в BestBudget остаётся обязательной. Не используйте нативный `completion` endpoint вместо `/v1`.

### GigaChat и сертификаты

[Авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api): POST OAuth с `Authorization: Basic ...`, `RqUID` (UUIDv4) и form-полем `scope`. Токен кешируется до истечения с запасом 60 секунд, одновременные обмены объединяются. Поддерживаются `expires_at` в секундах и миллисекундах. Секреты не логируются.

У GigaChat [частичная совместимость с OpenAI](https://developers.sber.ru/docs/ru/gigachat/guides/compatible-openai). Для пользовательских функций v1 использует `functions`, `function_call`, роль `function` и `functions_state_id`, см. [передачу результатов функции](https://developers.sber.ru/docs/ru/gigachat/guides/functions/generating-arguments-for-custom-functions). Адаптер переводит этот формат на границе `@ai-sdk/openai-compatible`; состояние функции сохраняется в SDK tool-call ID. Используются последовательные функции v1. Нативный запрос завершается целиком, после чего AI SDK передаёт текст UI потоком; задержка первого фрагмента отличается от нативного streaming у остальных провайдеров. Параллельный v2 API в эту фазу не входит.

При необходимости установите доверенные CA по [инструкции Сбера](https://developers.sber.ru/docs/ru/gigachat/certificates) и смонтируйте проверенный PEM только для чтения. Передайте `NODE_EXTRA_CA_CERTS=/app/certs/russian-trusted-ca.pem`. Не отключайте TLS (`NODE_TLS_REJECT_UNAUTHORIZED=0` не используется).

Пример Compose override (PEM заранее получен и проверен администратором):

```yaml
services:
  app:
    environment:
      NODE_EXTRA_CA_CERTS: /app/certs/russian-trusted-ca.pem
    volumes:
      - ./certs/russian-trusted-ca.pem:/app/certs/russian-trusted-ca.pem:ro
```

Для Helm можно смонтировать собственный ConfigMap:

```yaml
extraEnv:
  - name: NODE_EXTRA_CA_CERTS
    value: /app/certs/ca.pem
extraVolumes:
  - name: ai-ca
    configMap:
      name: trusted-ai-ca
extraVolumeMounts:
  - name: ai-ca
    mountPath: /app/certs
    readOnly: true
```

## Приватность и история

- `aggregates` по умолчанию: суммы по категориям/месяцам, имена и балансы счетов, категории, регулярные правила, бюджеты, цели, кредиты и прогноз. Описания отдельных операций, заметки кредитов/целей и комментарии взносов не отправляются.
- `detailed`: дополнительно ограниченный поиск операций с названиями и описаниями/контрагентами. Не более 20 записей на страницу; курсор и период до 366 дней.
- Провайдер получает ваши сообщения и историю текущего диалога, включая уже полученные результаты инструментов. Не вставляйте секреты в чат. Отметка self-hosted показывает заявленное администратором размещение; адрес назначения всегда виден в согласии.
- Диалоги приватны для создавшего их пользователя внутри семьи. Удаление своего диалога каскадно удаляет сообщения и предложения, сохраняя уже применённые финансовые изменения и аудит. Учёт использования сохраняется до удаления пользователя/семьи.
- Смена провайдера, base URL, модели или отметки self-hosted требует нового согласия. Диалог также привязан к уровню данных; после его смены начните новый диалог. Это исключает повторную отправку старых подробных результатов после перехода на aggregates.
- Названия и импортированные описания — недоверенные данные, даже если похожи на команды. Они передаются как JSON-данные результатов инструментов, системная инструкция запрещает следовать их указаниям. Текст модели не может применить предложение: API применения доступен только пользовательскому действию.
- HTML в markdown не исполняется; внешние изображения и ссылки из ответа не загружаются. CSP не расширяется для провайдеров: запросы идут только с сервера. PWA не кеширует финансовые страницы.
- Содержимое сообщений и снимки предложений хранятся в PostgreSQL; администратор инфраструктуры отвечает за доступ к БД и её резервным копиям. Шифрование API-ключа не является шифрованием всей истории чата.

## Предложения и конкурентные изменения

`propose_*` сохраняет `pending` proposal и ничего не меняет в финансовых сущностях. Для создания карточка показывает новую сущность без стрелок (лимит — название и сумма в месяц). Для изменений показаны только изменившиеся поля «было → станет». Пункты без фактических изменений исключаются до сохранения proposal; инструмент сообщает модели skippedUnchanged и status=unchanged, если весь пакет пуст. Пользователь выбирает пункты; недоступные по роли пункты отключены. **Изменить** заполняет поле уточнения, **Отклонить** закрывает оставшиеся пункты.

Применение повторно проверяет членство, согласие, права, базовую валюту/часовой пояс семьи, серверный снимок и версии. Весь выбранный пакет выполняется в одной транзакции через существующие сервисы. Вложенные сервисные транзакции — savepoints; ошибка любого пункта откатывает пакет. Категории и лимиты получили аддитивную колонку `version DEFAULT 1`; обычные изменения также увеличивают версии. Снимок лимита включает ID и исходную категорию, поэтому удаление, повторное создание и переименование не обходят проверку. Снимки также сохраняют версии и валюты связанных счетов/категорий: смена валюты ещё не использованного счёта после предложения вызывает конфликт. Для переводов обе суммы показываются в соответствующих валютах, отдельно для состояния до и после изменения. Целевая сумма цели выражена в валюте цели, а выделенная доля накоплений — в валюте привязанного счёта; единицы полей сохраняются в `fieldCurrencies`/`beforeFieldCurrencies`.

Результат каждого пункта сохраняет ссылку и ID сущности. Повторное применение не создаёт вторую сущность. Можно применить ещё не выбранные пункты позднее. Предложения действуют 7 дней; после изменения исходных данных запросите новое. Аудит существующих сервисов содержит действующего пользователя (`actorId`) и `meta.source = "ai"`, `meta.proposalId`; модель не является финансовым автором.

Для автопополнения цели сохраняется рассчитанный предварительный план с суммой, валютой, счетами и датами. Изменение расчёта между предложением и применением вызывает конфликт.

## Ограничения, стоимость и отказоустойчивость

- До 8 шагов генерации, до 32 вызовов инструментов за ход, последовательно; ответ до 2048 токенов на шаг.
- До 4000 символов пользовательского сообщения; контекст вместе со схемами инструментов ограничен 64 000 байт на шаг, результат инструмента — 24 000 байт. Большой диалог нужно начать заново, слишком большой результат — сузить периодом/поиском.
- До 10 запросов в минуту на пользователя; одна активная генерация на диалог. Лимиты и резерв токенов хранятся в БД и сериализуются блокировками, поэтому работают между репликами.
- Таймаут: 90 секунд на ход, 25 секунд на шаг, 15 секунд на инструмент. Автоматические сетевые повторы отключены. Пользователь видит ошибку и кнопку **Повторить**. Повтор обрезает контекст до исходного сообщения пользователя и создаёт новый ID ответа; незавершённые tool calls предыдущих попыток не отправляются в модель. Сами попытки остаются в приватной истории.
- Месяц учёта — UTC. `0` отключает квоту, но сохраняет учёт. Системный администратор видит токены входа, выхода и резерв по семьям.
- **Консервативный резерв:** перед запросом резервируется `8 × (64000 + 2048) = 528384` токена. При ненулевом лимите остаток должен покрывать резерв. Это намеренно строгий выбор, исключающий одновременный перерасход по нескольким диалогам без токенизаторов каждого провайдера. Для небольшой квоты уменьшите константы в контролируемом изменении; не обходите проверку на клиенте.
- Резерв действует только во время хода. При успехе, ошибке и отмене он освобождается: завершённые шаги учитываются по usage SDK (включая явно сообщённый ноль). При отсутствии usage применяется консервативная оценка: один токен на UTF-8 байт реально отправленного контекста/схем с техническим запасом 4096 байт и уже полученного текста/аргументов инструментов; выход ограничен maxOutputTokens шага. Не начавшиеся шаги не учитываются. Ошибка до первого фрагмента ответа освобождает оценку текущего шага; предыдущие завершённые шаги сохраняются. Числовые счётчики сохраняются перед запросом и при каждом фрагменте, без содержимого. Если процесс упал, при следующем запросе семьи под блокировкой освобождаются резервы через 10 минут после busyUntil: остаются только сохранённые счётчики, errorCode=interrupted. Старые строки без TTL также освобождаются. Повторная финализация идемпотентна.
- Счёт провайдера может учитывать дополнительные операции и собственные правила тарификации. BestBudget не хранит цены моделей и не обещает совпадения с денежным счётом провайдера. Проверки подключения не входят в семейную статистику.

## Периодический разбор бюджета

После согласия на ИИ откройте **Настройки → Семья → Периодический разбор бюджета** (из **Ассистент → Рекомендации** есть ссылка на этот блок). Владелец и администратор семьи могут выбрать **выключен / раз в неделю / раз в месяц**, день и время. По умолчанию расписание выключено; согласие само по себе его не включает. Используется часовой пояс семьи, а не браузера или scheduler. В коротких месяцах 29–31 число переносится на последний день. После простоя выполняется один разбор за текущий период; прошлые недели/месяцы не догоняются. Повторный час при переходе DST имеет тот же ключ периода.

**Разобрать сейчас** доступно owner/admin и при выключенном расписании. Лимит — **два ручных запуска в местный день на семью**, включая неудачные попытки и пропуск по квоте. Параллельный запрос возвращает текущий запуск. Для всех вызовов используются прежние квота, резерв токенов, rate limit, checkpoint usage, таймауты и повторная проверка согласия перед каждым шагом/инструментом. Небольшой ненулевой остаток, не покрывающий консервативный резерв, означает пропуск. Статус виден во входящих; уведомлений о пропусках нет.

Scheduler использует отдельный advisory lock `AI_REVIEW_JOB_LOCK=3`; это не задерживает обычные финансовые напоминания. В `ai_reviews` до вызова модели фиксируется уникальный `(household_id, period_key)`: `weekly:<понедельник>`, `monthly:<первое число>` либо `manual:<местная дата>:<1|2>`. Повторный тик, другая реплика и перезапуск не вызывают модель повторно за уже занятый период. Потеря lock/shutdown отменяет запрос; зависший запуск через 15 минут получает статус `interrupted`. Автоматического повторного списания за такой период нет; можно запустить вручную. Если `JOBS_ENABLED=false`, автоматические разборы и доставка выключены, ручная подготовка рекомендаций работает.

Разбор создаёт `createConversation(ctx, "review")` от системного автора **«ИИ-разбор»**. Владелец семьи — технический носитель членства/согласия и источник `recipientLocale` (сохранённый язык → последний язык браузера → English); автором финансовых изменений остаётся только применивший их пользователь. Смена языка интерфейса не переводит уже сохранённые инсайты; новые формируются на языке владельца. Системные диалоги скрыты из списка личных чатов. Входящие доступны членам семьи с `finance.read`, а каждый пункт применения повторно проверяет своё разрешение. Например, member видит лимит бюджета, но применить или отклонить изменение лимита может owner/admin. Системное администрирование не даёт доступа к чужим рекомендациям.

`get_review_period` даёт расходы и доходы за последние 30 дней, расходы за предыдущие 30 дней, календарные месячные лимиты/факт, регулярные обязательства, цели, кредиты и 90-дневный прогноз. Для больших результатов можно сузить данные существующими инструментами; общий предел результата — 24 КБ. Подробные операции доступны только через `search_transactions` при `detailed`. Названия и описания считаются недоверенными JSON-данными. Описания операций, комментарии взносов и заметки не включаются в агрегатную проекцию. Платежи не доказывают использование подписки: модель должна явно обозначать предположение о дубле/ненужной подписке. Досрочка кредита — информационная рекомендация для проверки в существующем кредитном симуляторе после обязательств и резерва; новый тип финансового события без предварительного расчёта не вводится.

Модель готовит пакеты через существующие `propose_*` и завершает разбор инструментом `submit_budget_review` с Zod-структурой: тип, ID сущности, направление, заголовок, объяснение в 1–3 предложения с цифрами, важность и ID пакетов. Сервер проверяет семью сущности и происхождение каждого proposal. Только успешный законченный разбор публикуется атомарно; лишние неприкреплённые пакеты закрываются. Job никогда не вызывает `applyProposal` и не материализует финансовые операции. Финансовые данные не пишутся в логи или usage.

Карточки поддерживают **Применить выбранное**, **Отклонить**, **Обсудить**. Обсуждение создаёт личный чат текущего пользователя с текстом рекомендации; без автоматического нового вызова модели. После изменения провайдера/уровня данных старые рекомендации не отображаются и не переносятся в новый чат. Применение сохраняет прежние транзакционные проверки версий и аудит `source=ai`/`proposalId`. Бейдж в навигации и виджет на обзоре показывают число ожидающих решения рекомендаций.

Отклонения хранятся в `ai_review_decisions` до удаления семьи и переживают удаление диалога. Для пакетов fingerprint рассчитывает сервер по типу пункта, сущности и направлению изменения числовых полей; формулировка, сумма в том же направлении, язык и перегруппировка не обходят отказ. Применённые пункты при последующем отклонении остальных не попадают в отказ. Для информационных инсайтов используется тип + проверенный ID сущности + направление. Внутри одного разбора повтор направления не создаёт вторую карточку. Успешный новый разбор атомарно заменяет прежние ожидающие рекомендации, сохраняя запреты отклонённых направлений; ошибка или пропуск по квоте оставляет прежние рекомендации открытыми.

Срок — **7 суток или до следующего успешного разбора**. Новая операция, смена даты и применение независимого пункта не закрывают остальные рекомендации. Общий серверный fingerprint состава/версий финансовых данных используется только для мягкой подсказки **«Данные изменились после разбора · Разобрать заново»**; местная дата в него не входит. Обычная материализация нетронутых плановых строк не меняет fingerprint. Любое значимое изменение включённых финансовых сущностей может показать подсказку; это намеренно обратимый выбор без автоматического скрытия или блокировки.

Актуальность проверяется **по пунктам**: renderer сравнивает текущий серверный `snapshot` зарегистрированного типа со снимком/версией и зависимостями пункта. Изменённый лимит, категория или другая связанная сущность помечают только этот пункт как устаревший с пояснением; остальные можно выбрать. Непосредственно перед применением общий обработчик повторяет ту же проверку с блокировкой строк. Выбор из нескольких пакетов одной карточки применяется в общей транзакции: конфликт в любом выбранном пункте откатывает весь выбор. Содержимое браузера не является основанием для записи. Карточка плоская, с цветной меткой важности и иконкой; пояснение срока приведено один раз на странице. Расписание использует `Segmented` и проектный `Select` и находится только в **Настройки → Семья**, чтобы входящие оставались списком решений; из рекомендаций доступна прямая ссылка на блок.

После успешного разбора отправляется только **«Новые рекомендации по бюджету: N»** со ссылкой на входящие. В настройках семьи разрешаются Telegram/Web Push/e-mail, а доставка дополнительно учитывает личные каналы, флаг рекомендаций, тихие часы, действующее членство/согласие и язык каждого получателя. E-mail по умолчанию выключен в личных настройках; после включения письма отправляются на адрес профиля через настроенный SMTP. Используется существующий `deliverOnce`: ключ `ai-review:<reviewId>` на пользователя/канал, для Push дополнительно на устройство; повторы и неизвестные исходы обрабатываются как у напоминаний. Истёкшие/заменённые рекомендации и отозванные предпочтения исключаются из доставки; несвязанная новая операция доставку не отменяет. Настройки обычных напоминаний и их digest не меняются.

Миграция `ai_budget_reviews` аддитивна: новые таблицы, `ai_proposals.author DEFAULT 'assistant'`, `notification_preferences.ai_review DEFAULT true` и `review_email DEFAULT false`; существующие суммы, согласие и история сохраняются. Снимки интерфейса: `docs/screenshots/ai/budget-review/` (входящие, обзор и настройки; синтетические данные, ru/en, 1280/375, light/dark). E2E сохраняет их только при `UPDATE_SCREENSHOTS=1`; mock не подтверждает качество или стоимость ответов реального провайдера.

## Расширение для фазы 2

Реестры в `src/server/ai/tools/*` и `proposal-registry.ts` открыты для новых определений; цикл генерации и API применения о конкретных именах инструментов не знают.

### Новый инструмент

1. Создайте модуль под `src/server/ai/tools/` и импортируйте его в `tools/index.ts`.
2. Вызовите `registerTool({ name, description, inputSchema, kind, detailed?, execute })`. Имя и описание на английском; Zod ограничивает период, размер и пагинацию.
3. `execute(input, { ctx, conversationId, messageId })` получает проверенный `HouseholdCtx`. Каждый запрос к финансовой таблице обязан содержать `householdId`. Переиспользуйте сервисы и проверки `assertCan`; не вызывайте материализацию/другую финансовую запись из read-инструмента.
4. Для aggregates используйте явную проекцию разрешённых полей. Не возвращайте целиком строки операций, расписаний с description, события кредитов или комментарии взносов.
5. Добавьте переводы `ai.tools.<name>` для состояния UI и интеграционный тест на изоляцию/приватность.

### Новый тип пункта

1. Зарегистрируйте `registerProposal(type, existingServiceSchema, { permission, snapshot, after, apply, operation })`. Используйте ту же Zod-схему, что сервис/server action, а не копию валидатора.
2. `snapshot` читает текущую сущность только своей семьи. При `lock=true` блокирует строку до конца применения. Версия и все финансовые зависимости, влияющие на расчёт, должны входить в снимок. Он создаётся сервером, модель не задаёт «было».
3. `operation` задаёт `create` или функцию выбора режима, по умолчанию `update`. `after` задаёт понятные пользователю поля будущего состояния. Для вычисляемой операции сначала реализуйте сервис предварительного расчёта; карточка обязана показывать сумму и дату до применения.
4. `apply` вызывает существующий сервис; он автоматически получает общую транзакцию через `withDb` (AsyncLocalStorage). Прямые SQL-изменения финансов из инструмента запрещены. Не запускайте фоновые задачи из этого контекста.
5. Добавьте тип в соответствующую группу `propose.ts` либо зарегистрируйте отдельный propose-инструмент. Добавьте `ai.kinds`, `ai.fields`, при необходимости `ai.values` в ru/en. Новые renderer-специфичные данные требуют отдельного UI и проверки 375px.
6. Проверьте отсутствие мутаций при propose, успешное применение, откат при ошибке второго пункта, конфликт, повторное применение, права и чужую семью.

`createConversation(ctx, kind)` поддерживает `chat`, `onboarding`, `review`. Для интервью фаза 2 использует `onboarding`; для разбора — `review`. Не вызывайте пользовательский `applyProposal` из scheduler: периодический разбор может только подготовить предложение с явно определённым автором и последующим пользовательским подтверждением. Механика расписания/уведомлений, хранение прогресса интервью и сценарные промпты остаются задачами фазы 2.

## Составить бюджет с ИИ

После создания семьи владелец сначала включает ИИ и подтверждает согласие в **Настройки → Семья → ИИ для семьи**. Под формой появляется предложение пройти интервью. На обзоре карточка **Составить бюджет с ИИ** доступна, пока нет лимитов или регулярных правил; в пустом ассистенте есть такой же стартер для повторного планирования. Интервью доступно владельцу и администратору семьи (`catalog.manage`); member сохраняет обычные права на операции, но не может начать интервью, отправлять в него сообщения или применить его пакет после понижения роли.

Диалог имеет `kind=onboarding`. В списке он отмечен иконкой интервью и получает локализованное имя «Составление бюджета · 23 окт.» / «Budget setup · Oct 23» по дате начала в TZ семьи. Ответы пользователя его не меняют. В меню диалога можно задать своё имя или вернуть автоматическое; пользовательское имя сохраняется при продолжении и смене языка. Старые интервью с именем из последнего ответа тоже показываются с корректным автоматическим именем. Переименование проверяет владельца приватного диалога, занятость и версию. Локализованная инструкция ведёт через доходы, обязательные платежи, переменные расходы, цели и предпочтения. `get_interview_context` читает существующий план через разрешённые агрегатные проекции; описания операций, заметки и комментарии не добавляются. `interview_step` возвращает 1–2 вопроса и до 6 быстрых ответов. Степпер и кнопки восстанавливаются из обычных tool-частей сообщений; отдельной таблицы или движка интервью нет. **Продолжить позже** возвращает на обзор; стартер открывает незавершённый диалог с текущим согласием. После полного применения следующий запуск создаёт новое интервью. Контролы заблокированы до гидрации.

`propose_budget_plan` готовит один пакет (до 20 пунктов), резюме следующего полного месяца и прогноз до его конца. Существующие категории сопоставляются по виду и имени, правила — по ID либо названию/счёту/дню, цели — по ID либо имени. Неоднозначные совпадения требуют явного ID. Повторный неизменённый план получает `status=unchanged`; существующие сущности редактируются через версии. Новый график заменяет будущие начисления редактируемого правила в предварительном прогнозе; выполненные и прежние просроченные операции сохраняются. Предпросмотр не создаёт категорий, правил, операций, лимитов или целей.

Месячное резюме содержит доходы, обязательные платежи, лимиты, дополнительный резерв на переменные расходы, накопления и остаток. Для категории с регулярным платежом дополнительный резерв равен `max(лимит − регулярные расходы, 0)`, чтобы не считать одну сумму дважды. Ежедневный прогноз учитывает только платежи с датами; недатированные траты внутри лимитов не распределяются по дням. Это семейный прогноз, а не отдельный контроль ликвидности каждого счёта. При отсутствии курсов итоги неполные, предупреждения передаются модели.

Для ещё не существующей категории зарегистрированы `recurring.planned` и `budget.planned` на схемах сервисов `budget-plan.ts`. В пакете они зависят от `category.create`; чекбоксы подбирают обязательную категорию и снимают зависимые пункты при её отмене. API проверяет зависимости повторно и применяет пункты в сохранённом порядке: категории → регулярные → лимиты → цели, одной транзакцией. Можно применить категорию первой, а остальные пункты позже; сервер проверит её поля и фактический ID результата. Ошибка любого пункта откатывает весь выбранный набор, включая материализованные плановые операции. Ссылки результата ведут в календарь, бюджеты и созданные сущности.

Карточки создания используют резюме по типу пункта (`src/domain/ai/summaries.ts`, ICU-шаблоны `ai.summaries.*` ru/en), а не перечень полей. Основная строка содержит название, сумму и назначение; детали сохраняют важные даты, счета, условия и автопополнение. Код валюты добавляется только для валюты, отличной от базовой; обе суммы валютного перевода сохраняются. Для изменений остаётся сравнение «было → стало».

`goal.create_automated` объединяет новую цель и явно согласованное автопополнение. `previewNewGoalAutomation` подставляет будущую цель в штатный расчёт распределения накоплений без записи в БД; карточка показывает сумму, валюты, счета и даты до подтверждения. ID будущей цели выделяется сервером заранее, чтобы порядок распределения совпадал с предпросмотром. Применение перепроверяет расчёт и использует обычные `createGoal`/`automateGoal` в общей транзакции. Для автопополнения нужен существующий накопительный счёт; интервью может предложить ручную цель, если его нет. Автопополнения нескольких новых целей на один накопительный счёт оформляются отдельными планами. Изменение параметров существующей цели и включение её первого автопополнения требуют двух подтверждений: сначала изменение, затем новый запрос автоматизации; модель получает предупреждение. Уже настроенное автопополнение повторно не создаётся.

Все вызовы модели идут через штатный `chatResponse` с общими квотой, учётом токенов, согласием и лимитами. Финансовых записей из read-инструментов и вызовов `applyProposal` из scheduler нет. Аддитивная миграция `0013_ai_conversation_titles` добавляет `custom_title` (nullable) и `version` (NOT NULL DEFAULT 1) в `ai_conversations`; существующие диалоги и финансовые данные сохраняются. Интеграционные тесты и e2e используют только синтетические данные и mock-модель; они не подтверждают качество интервью у конкретного внешнего провайдера. Скриншоты ru/en, 1280/375, light/dark: `docs/screenshots/ai/interview/`.

## Тестовый провайдер

Unit/integration используют `MockLanguageModelV3` из `ai/test`. Для Playwright создаётся отдельный production-style **тестовый артефакт** с `NEXT_PUBLIC_AI_TEST_BUILD=1`; при запуске также нужен `AI_TEST_MODE=1`. В таком артефакте можно выбрать `mock` в админке или передать `AI_PROVIDER=mock`, `AI_MODEL=test-budget`, `AI_ENABLED=true` (после этого всё равно нужны проверка подключения и согласие).

Обычная production-сборка фиксирует отсутствие build-маркера через `next.config.ts`; `pnpm build` дополнительно проверяет готовый manifest и отказывается упаковывать тестовый артефакт: установка одного runtime `AI_PROVIDER=mock`/`AI_TEST_MODE` его не включает. Тестовый артефакт не публикуйте как production-образ. E2E включают mock через UI, чтобы проверить реальное сохранение конфигурации, затем согласие → streaming → 2 из 3 пунктов → лимиты в БД.

Источники API: [AI SDK: tools](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling), [persistence](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence), [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [OpenAI models](https://developers.openai.com/api/reference/resources/models/methods/list). Версии пакетов зафиксированы в `package.json` и lockfile.
