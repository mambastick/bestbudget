# ИИ-ассистент

Фаза 1 предоставляет чат, настройки, инструменты чтения и подтверждаемые предложения. Интервью для составления бюджета и периодический разбор будут добавлены в фазе 2. Ассистент выключен по умолчанию; без согласия семьи финансовые данные провайдеру не отправляются.

## Включение

1. Системный администратор открывает **Администрирование → ИИ-ассистент**: выбирает провайдера, адрес, модель, при необходимости ключ, температуру и лимит токенов.
2. **Получить модели** запрашивает каталог провайдера. Поле модели остаётся редактируемым: можно ввести идентификатор вручную. Каталог сам по себе не подтверждает поддержку инструментов.
3. **Проверить подключение** выполняет небольшой запрос с принудительным вызовом `connection_check`. Затем сохраните настройки с включённым флагом. При включении проверка выполняется повторно. Модель без tool calling использовать нельзя. Проверка может тарифицироваться провайдером; финансовых данных в ней нет.
4. Владелец семьи открывает **Настройки → Семья → ИИ для семьи**, проверяет провайдера, модель и адрес назначения, выбирает уровень данных, включает ассистента и подтверждает согласие.
5. В навигации и на обзоре появляется **Ассистент**. Можно создать диалог, изучить расходы и применить выбранные пункты карточки.

Системный администратор видит только конфигурацию и статистику токенов по семьям. Само администрирование не даёт доступа к финансовым данным чужой семьи. Доступные в проекте семейные роли — owner/admin/member; ИИ использует существующую матрицу `can(...)`, отдельную роль viewer эта фаза не вводит.

## Конфигурация через ENV

При непустом `AI_PROVIDER` вся конфигурация берётся из ENV, поля в админке доступны только для чтения. Секрет из БД при этом не подмешивается. После изменения ENV перезапустите приложение и выполните **Проверить подключение** в админке. Результат проверки привязан к конфигурации, включая ключ; при смене подключения его нужно проверить заново. `AI_ENABLED=true` без проверки и согласия семьи не открывает API.

| Переменная | Назначение |
|---|---|
| `AI_PROVIDER` | `openai`, `openai_compatible`, `anthropic`, `google`, `gigachat`; пусто — настройки БД |
| `AI_BASE_URL` | HTTP(S) base URL; для совместимых серверов обычно заканчивается на `/v1` |
| `AI_API_KEY` | API key; для GigaChat — ключ авторизации Base64(client_id:client_secret), без префикса `Basic` |
| `AI_MODEL` | Идентификатор модели, без встроенного значения по умолчанию |
| `AI_ENABLED` | `false` по умолчанию; включается только явно |
| `AI_TEMPERATURE` | Необязательно, диапазон 0–2; конкретная модель может ограничивать параметр |
| `AI_MONTHLY_TOKEN_LIMIT` | Целое число, лимит на каждую семью; `0` — без лимита |
| `AI_SELF_HOSTED` | `false`; отметка администратора о размещении модели на своём сервере |
| `AI_GIGACHAT_SCOPE` | `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B`, `GIGACHAT_API_CORP` |
| `AI_GIGACHAT_AUTH_URL` | По умолчанию `https://ngw.devices.sberbank.ru:9443/api/v2/oauth` |
| `NODE_EXTRA_CA_CERTS` | Путь к PEM с дополнительными доверенными CA; применяется Node.js при старте |

Не помещайте ключ в base URL, параметры URL или логи. Ключ из формы хранится зашифрованным через `src/lib/crypto.ts` (AES-256-GCM), в браузер не возвращается. Пустое поле сохраняет ключ, отдельный флаг удаляет его. Сохраните `ENCRYPTION_KEY`/`BETTER_AUTH_SECRET` вместе с защищённой резервной копией.

Compose передаёт переменные приложению; примеры в `.env.example` закомментированы. В Helm используйте `ai.*`, а ключ передавайте через `existingSecret` → `AI_API_KEY` либо защищённый `ai.apiKey`. Пустой `ai.provider` оставляет управление в UI.

## Провайдеры

Имена ниже — примеры настройки, а не список зашитых моделей. Выбирайте модель, доступную вашему аккаунту и поддерживающую инструменты. Реальное подключение каждого платного провайдера требует собственного ключа; автоматические тесты используют mock и не подтверждают доступность конкретного аккаунта, тариф или качество модели.

| Провайдер | Тип | Base URL | Модель / ключ |
|---|---|---|---|
| OpenAI | `openai` | `https://api.openai.com/v1` | Из каталога OpenAI, API key; используется Responses API |
| Anthropic | `anthropic` | `https://api.anthropic.com/v1` | Из Models API, Anthropic API key |
| Gemini | `google` | `https://generativelanguage.googleapis.com/v1beta` | Из каталога Gemini, Google API key |
| OpenRouter | `openai_compatible` | `https://openrouter.ai/api/v1` | Например идентификатор `vendor/model` из каталога, ключ OpenRouter |
| Ollama | `openai_compatible` | `http://ollama:11434/v1` | Установленная tool-capable модель; ключ может быть пустым; каталог `/v1/models`, fallback `/api/tags` |
| LM Studio | `openai_compatible` | `http://host.docker.internal:1234/v1` | Загруженная модель с tool calling; адрес должен быть доступен из контейнера |
| vLLM / LocalAI / llama.cpp server | `openai_compatible` | URL вашего сервера + `/v1` | Имя опубликованной модели; ключ по настройке сервера |
| DeepSeek / Groq / Together / Mistral | `openai_compatible` | OpenAI-compatible base URL из документации выбранного сервиса | Каталог сервиса или ручной ввод; ключ этого сервиса |
| Yandex Cloud AI Studio / YandexGPT | `openai_compatible` | `https://ai.api.cloud.yandex.net/v1` | URI `gpt://<folder_ID>/<model_ID>/latest`, API key сервисного аккаунта с правами на модель |
| GigaChat | `gigachat` | `https://api.giga.chat/v1` | Из `/models`, ключ авторизации и соответствующий scope |

OpenAI-совместимые endpoints различаются поддержкой моделей, схем и учёта токенов. Обязателен успешный тест инструмента; одного текстового ответа недостаточно. Если endpoint не публикует каталог, используйте ручной ввод. Каталоги могут содержать модели без tool calling.

Yandex документирует OpenAI-compatible endpoint и URI моделей в [инструкции интеграции](https://yandex.cloud/en/docs/tutorials/ml-ai/ai-model-ide-integration). Доступность инструментов зависит от модели и API; проверка подключения в BestBudget остаётся обязательной. Не используйте нативный `completion` endpoint вместо `/v1`.

### GigaChat и сертификаты

[Авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api): POST OAuth с `Authorization: Basic ...`, `RqUID` (UUIDv4) и form-полем `scope`. Токен кешируется до истечения с запасом 60 секунд, одновременные обмены объединяются. Поддерживаются `expires_at` в секундах и миллисекундах. Секреты не логируются.

У GigaChat [частичная совместимость с OpenAI](https://developers.sber.ru/docs/ru/gigachat/guides/compatible-openai). Для пользовательских функций v1 использует `functions`, `function_call`, роль `function` и `functions_state_id`, см. [передачу результатов функции](https://developers.sber.ru/docs/ru/gigachat/guides/functions/generating-arguments-for-custom-functions). Адаптер переводит этот формат на границе `@ai-sdk/openai-compatible`; состояние функции сохраняется в SDK tool-call ID. Используются последовательные функции v1. Нативный запрос завершается целиком, после чего AI SDK передаёт текст UI потоком; задержка первого фрагмента отличается от нативного streaming у остальных провайдеров. Параллельный v2 API в эту фазу не входит.

При необходимости установите доверенные CA по [инструкции Сбера](https://developers.sber.ru/docs/ru/gigachat/certificates) и смонтируйте проверенный PEM только для чтения. Передайте `NODE_EXTRA_CA_CERTS=/app/certs/russian-trusted-ca.pem`. Не отключайте TLS (`NODE_TLS_REJECT_UNAUTHORIZED=0` не используется).

Пример Compose override (PEM заранее получен и проверен администратором):

```yaml
services:
  app:
    environment:
      NODE_EXTRA_CA_CERTS: /app/certs/russian-trusted-ca.pem
    volumes:
      - ./certs/russian-trusted-ca.pem:/app/certs/russian-trusted-ca.pem:ro
```

Для Helm можно смонтировать собственный ConfigMap:

```yaml
extraEnv:
  - name: NODE_EXTRA_CA_CERTS
    value: /app/certs/ca.pem
extraVolumes:
  - name: ai-ca
    configMap:
      name: trusted-ai-ca
extraVolumeMounts:
  - name: ai-ca
    mountPath: /app/certs
    readOnly: true
```

## Приватность и история

- `aggregates` по умолчанию: суммы по категориям/месяцам, имена и балансы счетов, категории, регулярные правила, бюджеты, цели, кредиты и прогноз. Описания отдельных операций, заметки кредитов/целей и комментарии взносов не отправляются.
- `detailed`: дополнительно ограниченный поиск операций с названиями и описаниями/контрагентами. Не более 20 записей на страницу; курсор и период до 366 дней.
- Провайдер получает ваши сообщения и историю текущего диалога, включая уже полученные результаты инструментов. Не вставляйте секреты в чат. Отметка self-hosted показывает заявленное администратором размещение; адрес назначения всегда виден в согласии.
- Диалоги приватны для создавшего их пользователя внутри семьи. Удаление своего диалога каскадно удаляет сообщения и предложения, сохраняя уже применённые финансовые изменения и аудит. Учёт использования сохраняется до удаления пользователя/семьи.
- Смена провайдера, base URL, модели или отметки self-hosted требует нового согласия. Диалог также привязан к уровню данных; после его смены начните новый диалог. Это исключает повторную отправку старых подробных результатов после перехода на aggregates.
- Названия и импортированные описания — недоверенные данные, даже если похожи на команды. Они передаются как JSON-данные результатов инструментов, системная инструкция запрещает следовать их указаниям. Текст модели не может применить предложение: API применения доступен только пользовательскому действию.
- HTML в markdown не исполняется; внешние изображения и ссылки из ответа не загружаются. CSP не расширяется для провайдеров: запросы идут только с сервера. PWA не кеширует финансовые страницы.
- Содержимое сообщений и снимки предложений хранятся в PostgreSQL; администратор инфраструктуры отвечает за доступ к БД и её резервным копиям. Шифрование API-ключа не является шифрованием всей истории чата.

## Предложения и конкурентные изменения

`propose_*` сохраняет `pending` proposal и ничего не меняет в финансовых сущностях. В карточке показаны тип изменения, название, суммы/даты и изменённые поля «было → станет». Пользователь выбирает пункты; недоступные по роли пункты отключены. **Изменить** заполняет поле уточнения, **Отклонить** закрывает оставшиеся пункты.

Применение повторно проверяет членство, согласие, права, базовую валюту/часовой пояс семьи, серверный снимок и версии. Весь выбранный пакет выполняется в одной транзакции через существующие сервисы. Вложенные сервисные транзакции — savepoints; ошибка любого пункта откатывает пакет. Категории и лимиты получили аддитивную колонку `version DEFAULT 1`; обычные изменения также увеличивают версии. Снимок лимита включает ID и исходную категорию, поэтому удаление, повторное создание и переименование не обходят проверку. Снимки также сохраняют версии и валюты связанных счетов/категорий: смена валюты ещё не использованного счёта после предложения вызывает конфликт. Для переводов обе суммы показываются в соответствующих валютах, отдельно для состояния до и после изменения. Целевая сумма цели выражена в валюте цели, а выделенная доля накоплений — в валюте привязанного счёта; единицы полей сохраняются в `fieldCurrencies`/`beforeFieldCurrencies`.

Результат каждого пункта сохраняет ссылку и ID сущности. Повторное применение не создаёт вторую сущность. Можно применить ещё не выбранные пункты позднее. Предложения действуют 7 дней; после изменения исходных данных запросите новое. Аудит существующих сервисов содержит действующего пользователя (`actorId`) и `meta.source = "ai"`, `meta.proposalId`; модель не является финансовым автором.

Для автопополнения цели сохраняется рассчитанный предварительный план с суммой, валютой, счетами и датами. Изменение расчёта между предложением и применением вызывает конфликт.

## Ограничения, стоимость и отказоустойчивость

- До 8 шагов генерации, до 32 вызовов инструментов за ход, последовательно; ответ до 2048 токенов на шаг.
- До 4000 символов пользовательского сообщения; контекст вместе со схемами инструментов ограничен 64 000 байт на шаг, результат инструмента — 24 000 байт. Большой диалог нужно начать заново, слишком большой результат — сузить периодом/поиском.
- До 10 запросов в минуту на пользователя; одна активная генерация на диалог. Лимиты и резерв токенов хранятся в БД и сериализуются блокировками, поэтому работают между репликами.
- Таймаут: 90 секунд на ход, 25 секунд на шаг, 15 секунд на инструмент. Автоматические сетевые повторы отключены. Пользователь видит ошибку и кнопку **Повторить**. Повтор обрезает контекст до исходного сообщения пользователя и создаёт новый ID ответа; незавершённые tool calls предыдущих попыток не отправляются в модель. Сами попытки остаются в приватной истории.
- Месяц учёта — UTC. `0` отключает квоту, но сохраняет учёт. Системный администратор видит токены входа, выхода и резерв по семьям.
- **Консервативный резерв:** перед запросом резервируется `8 × (64000 + 2048) = 528384` токена. При ненулевом лимите остаток должен покрывать резерв. Это намеренно строгий выбор, исключающий одновременный перерасход по нескольким диалогам без токенизаторов каждого провайдера. Для небольшой квоты уменьшите константы в контролируемом изменении; не обходите проверку на клиенте.
- После успешного ответа резерв заменяется фактическим использованием SDK. Если провайдер не сообщил usage, используется верхняя оценка. После ошибки/отмены/падения процесса резерв сохраняется до конца месяца: это консервативный учёт возможного оплаченного запроса, а не подтверждение реально потраченных токенов. Администратор может увеличить лимит. Автоматическое «освобождение зависшего резерва» без сверки с провайдером не выполняется.
- Счёт провайдера может учитывать дополнительные операции и собственные правила тарификации. BestBudget не хранит цены моделей и не обещает совпадения с денежным счётом провайдера. Проверки подключения не входят в семейную статистику.

## Расширение для фазы 2

Реестры в `src/server/ai/tools/*` и `proposal-registry.ts` открыты для новых определений; цикл генерации и API применения о конкретных именах инструментов не знают.

### Новый инструмент

1. Создайте модуль под `src/server/ai/tools/` и импортируйте его в `tools/index.ts`.
2. Вызовите `registerTool({ name, description, inputSchema, kind, detailed?, execute })`. Имя и описание на английском; Zod ограничивает период, размер и пагинацию.
3. `execute(input, { ctx, conversationId, messageId })` получает проверенный `HouseholdCtx`. Каждый запрос к финансовой таблице обязан содержать `householdId`. Переиспользуйте сервисы и проверки `assertCan`; не вызывайте материализацию/другую финансовую запись из read-инструмента.
4. Для aggregates используйте явную проекцию разрешённых полей. Не возвращайте целиком строки операций, расписаний с description, события кредитов или комментарии взносов.
5. Добавьте переводы `ai.tools.<name>` для состояния UI и интеграционный тест на изоляцию/приватность.

### Новый тип пункта

1. Зарегистрируйте `registerProposal(type, existingServiceSchema, { permission, snapshot, after, apply })`. Используйте ту же Zod-схему, что сервис/server action, а не копию валидатора.
2. `snapshot` читает текущую сущность только своей семьи. При `lock=true` блокирует строку до конца применения. Версия и все финансовые зависимости, влияющие на расчёт, должны входить в снимок. Он создаётся сервером, модель не задаёт «было».
3. `after` задаёт понятные пользователю поля будущего состояния. Для вычисляемой операции сначала реализуйте сервис предварительного расчёта; карточка обязана показывать сумму и дату до применения.
4. `apply` вызывает существующий сервис; он автоматически получает общую транзакцию через `withDb` (AsyncLocalStorage). Прямые SQL-изменения финансов из инструмента запрещены. Не запускайте фоновые задачи из этого контекста.
5. Добавьте тип в соответствующую группу `propose.ts` либо зарегистрируйте отдельный propose-инструмент. Добавьте `ai.kinds`, `ai.fields`, при необходимости `ai.values` в ru/en. Новые renderer-специфичные данные требуют отдельного UI и проверки 375px.
6. Проверьте отсутствие мутаций при propose, успешное применение, откат при ошибке второго пункта, конфликт, повторное применение, права и чужую семью.

`createConversation(ctx, kind)` поддерживает `chat`, `onboarding`, `review`. Для интервью фаза 2 использует `onboarding`; для разбора — `review`. Не вызывайте пользовательский `applyProposal` из scheduler: периодический разбор может только подготовить предложение с явно определённым автором и последующим пользовательским подтверждением. Механика расписания/уведомлений, хранение прогресса интервью и сценарные промпты остаются задачами фазы 2.

## Тестовый провайдер

Unit/integration используют `MockLanguageModelV3` из `ai/test`. Для Playwright создаётся отдельный production-style **тестовый артефакт** с `NEXT_PUBLIC_AI_TEST_BUILD=1`; при запуске также нужен `AI_TEST_MODE=1`. В таком артефакте можно выбрать `mock` в админке или передать `AI_PROVIDER=mock`, `AI_MODEL=test-budget`, `AI_ENABLED=true` (после этого всё равно нужны проверка подключения и согласие).

Обычная production-сборка фиксирует отсутствие build-маркера через `next.config.ts`; `pnpm build` дополнительно проверяет готовый manifest и отказывается упаковывать тестовый артефакт: установка одного runtime `AI_PROVIDER=mock`/`AI_TEST_MODE` его не включает. Тестовый артефакт не публикуйте как production-образ. E2E включают mock через UI, чтобы проверить реальное сохранение конфигурации, затем согласие → streaming → 2 из 3 пунктов → лимиты в БД.

Источники API: [AI SDK: tools](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling), [persistence](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence), [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [OpenAI models](https://developers.openai.com/api/reference/resources/models/methods/list). Версии пакетов зафиксированы в `package.json` и lockfile.
