# Напоминания о платежах

## Быстрый старт за 3 шага

1. Откройте [@BotFather](https://t.me/BotFather), выполните `/newbot`, создайте отдельного бота для BestBudget и скопируйте токен.
2. В BestBudget откройте **Админка → Уведомления** (страница «Администрирование»), выключите «Отключить бота»,
   вставьте токен и нажмите **Сохранить бота**. Для сервера за NAT оставьте **Polling**.
3. В **Настройки → Профиль и безопасность** нажмите **Подключить Telegram** → **Открыть Telegram** → «Запустить» в боте.
   Вернитесь в профиль, нажмите **Проверить подключение**, включите **Уведомления в Telegram** для текущей семьи и сохраните.

Ссылка привязки одноразовая и действует 10 минут. Новая ссылка заменяет предыдущую; не пересылайте её другим людям.

Уведомления выключены по умолчанию. В **Настройки → Профиль и безопасность** подключите Telegram и/или браузер,
затем включите нужные каналы для текущей семьи. Повторите настройку для остальных семей.
События, время сводки и тихие часы считаются в часовом поясе семьи, независимо от часового пояса сервера.

## Telegram

Пустое поле токена при сохранении оставляет прежний токен; «Отключить бота» удаляет его из БД.
Администратор может отправить тест только в свой Telegram, подключённый в профиле.

### Как выбрать режим

**Polling — выбор по умолчанию для домашнего сервера, NAS и установки за NAT.**
Нужен только исходящий HTTPS-доступ к `api.telegram.org`; публичный адрес и входящий порт не требуются.
Непрерывный цикл вызывает `getUpdates(timeout: 30)` и сразу начинает следующий запрос после ответа,
независимо от минутной задачи доставки напоминаний. Поэтому обычная команда или нажатие кнопки не ждут минутного тика.
`answerCallbackQuery` отправляется сразу, до чтения и изменения платежа; результат подтверждения приходит сообщением.
При ошибках применяется backoff 1–30 секунд; для 409 Conflict — минимум 5 секунд, для 429 учитывается `retry_after`.
Если возникает 409, убедитесь, что этот токен не использует другой экземпляр приложения или сторонний polling-клиент.

**Webhook выбирайте, если у приложения уже есть публичный HTTPS-адрес, доступный Telegram.**
Запросы поступают напрямую в приложение; отдельного polling-запроса нет. Настройка описана ниже.
Для обычной self-hosted установки функционально достаточно polling.


Команды: `/today` — платежи сегодня/завтра по всем доступным семьям; `/balance` — фактические балансы;
`/stop` — удалить привязку и остановить Telegram. Команды работают только в личном чате.
Кнопка «✅ Оплачено» подтверждает плановую операцию через обычный сервис: проверяются пользователь, актуальные права и версия.
Изменённая, уже подтверждённая, пропущенная или чужая операция не подтверждается. «Открыть» ведёт в приложение;
для HTTP-установок вместо URL-кнопки передаётся текстовая ссылка. При активном сеансе ссылка автоматически выбирает семью уведомления, предварительно проверяя членство.

Альтернатива админке — `TELEGRAM_BOT_TOKEN` (приоритет над БД). В этом случае форма доступна только для чтения.
`TELEGRAM_MODE=polling|webhook` отдельно переопределяет режим; если переменная отсутствует, действует настройка из БД.
После смены бота привязки удаляются: пользователи подключают нового бота заново. Ротация токена того же бота сохраняет привязки.
Остановите старый экземпляр BestBudget при переносе на другую БД: advisory lock координирует реплики только внутри одной БД.

### Webhook

Нужен публичный HTTPS `APP_URL`, доступный Telegram. Выберите Webhook в админке (или `TELEGRAM_MODE=webhook`).
Контроллер Telegram сам вызывает `setWebhook` на `${APP_URL}/api/telegram/webhook` с `secret_token`.
Секрет генерируется и хранится зашифрованным; можно задать `TELEGRAM_WEBHOOK_SECRET` (URL-safe, до 256 символов).
Endpoint принимает только запросы с правильным `X-Telegram-Bot-Api-Secret-Token` и ограничивает тело 32 КиБ.
Переход обратно в polling вызывает `deleteWebhook`, не удаляя очередь Telegram. Статус username, последнего апдейта и ошибок — в админке.
Режимы и ограничения описаны в [Telegram Bot API](https://core.telegram.org/bots/api).

## Web Push

Нужен HTTPS (исключение браузеров — localhost), поддержка Service Worker/Push API и разрешение пользователя.
В профиле нажмите **Включить уведомления в браузере**, разрешите уведомления, затем включите канал для семьи и сохраните.
**Тест Web Push** отправляет тест на подключённые устройства профиля. Удаление устройства в списке прекращает доставку на него;
повторное подключение возможно той же кнопкой. При запрете разрешения измените настройки сайта в браузере и повторите.

На **iPhone/iPad** сначала добавьте приложение через Safari → «Поделиться» → «На экран Домой» и запустите с экрана «Домой».
Web Push поддерживается для таких веб-приложений начиная с iOS/iPadOS 16.4. В обычной вкладке Safari включить push нельзя.
См. [WebKit: Web Push for Web Apps on iOS and iPadOS](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

VAPID-пара генерируется при первом старте scheduler-а (или первом открытии настроек) под блокировкой строки БД.
Приватный ключ зашифрован. Можно задать **оба** `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY`; они имеют приоритет над БД.
`VAPID_SUBJECT` — контакт `mailto:` или публичный HTTPS URL; по умолчанию HTTPS APP_URL, для HTTP — `mailto:admin@localhost`.
Сохраняйте ключи и ENCRYPTION_KEY в резервной копии; после их замены браузеры подключаются заново.

Разрешены HTTPS endpoints FCM, Mozilla, Apple и Windows (`fcm.googleapis.com`, `*.updates.push.services.mozilla.com`,
`*.push.apple.com`, `*.notify.windows.com`). Произвольные URL запрещены для защиты от SSRF.
Исходящий HTTPS к соответствующим службам должен быть доступен. Ответ 404/410 удаляет подписку.
Service worker `/sw.js` **не кеширует приложение** и не перехватывает запросы страниц.

## События и дедупликация

- Ближайший платёж: одно уведомление на операцию и её дату в выбранном окне 0–30 дней. Включены расходы и переводы, доходы не включены.
- Просрочка: одно уведомление на операцию и дату после наступления просрочки, с текущим числом дней ожидания.
- Кассовый разрыв: первый отрицательный день прогноза на 30 дней, один раз на эту дату. Если разрыв сохраняется сегодня,
  в следующий день может прийти новое предупреждение с новой датой.
- Бюджет: расходы по факту, точное сравнение целых копеек; одно предупреждение на категорию, порог и календарный месяц.
  Порог — процент **сверх** лимита (15 означает 115% лимита). В сводках уже переданное бюджетное предупреждение также не повторяется.
- Ежедневная сводка заменяет отдельные сообщения, максимум одна в день на канал/устройство. Если приложение было выключено в выбранное
  время, сводка отправляется при следующем прогоне в этот же календарный день. Платежи и просрочка в сводке показывают текущую ситуацию ежедневно.
- Тихие часы откладывают уведомления; одинаковые начало и конец отключают этот интервал. Если время сводки попадает в тихие часы,
  она приходит после их окончания (и после выбранного времени в текущем дне). Команды и явные тесты отправляются сразу.

Сообщения ограничены по длине; длинная сводка сокращается со ссылкой на приложение. Telegram API вызывается не чаще 25 раз/с,
сообщения в один чат — не чаще одного за 1,1 секунды. Один job ограничен 250 реальными попытками доставки.
При 429/5xx выполняются до четырёх попыток с backoff от двух минут, учитывается Telegram `retry_after`.
Повторяются только всё ещё актуальные события, при действующем членстве и включённом канале.

Сначала в БД фиксируется попытка, затем выполняется HTTP-запрос. После перезапуска уже отправленные сообщения не повторяются.
При сетевом обрыве/аварии между этими шагами результат может остаться неизвестным: статус `unknown`, автоматического повтора нет.
Это предотвращает дубликаты, но допускает пропуск уведомления. Сообщения не являются гарантированным способом проведения платежей.
В админке видны безопасные коды ошибок (`telegram_429`, `push_410`, `*_unknown`), число попыток и статус, без финансового содержимого.

## Переменные окружения

ENV имеют приоритет над настройками из БД. Для нескольких реплик используйте одинаковые ENV и одну БД.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | обязательна | Подключение к общей PostgreSQL для данных, координации реплик и advisory locks. |
| `BETTER_AUTH_SECRET` | обязательна, минимум 32 символа | Сессии и подпись одноразовых Telegram-ссылок; источник производного ключа шифрования. |
| `APP_URL` | обязательна | Адрес приложения для ссылок; для webhook нужен публичный HTTPS. |
| `JOBS_ENABLED` | `true` | `false` останавливает минутную job и непрерывный контроллер Telegram. |
| `TELEGRAM_BOT_TOKEN` | токен из админки | Токен бота; при наличии поле токена в админке доступно только для чтения. |
| `TELEGRAM_MODE` | настройка БД, изначально `polling` | Переопределяет режим: `polling` или `webhook`. |
| `TELEGRAM_WEBHOOK_SECRET` | генерируется и шифруется в БД | Секрет заголовка webhook: 1–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-`. |
| `VAPID_PUBLIC_KEY` | генерируется и сохраняется в БД | Публичный ключ Web Push; задаётся только вместе с приватным. |
| `VAPID_PRIVATE_KEY` | генерируется и шифруется в БД | Приватный ключ Web Push; задаётся только вместе с публичным. |
| `VAPID_SUBJECT` | HTTPS `APP_URL`, для HTTP — `mailto:admin@localhost` | Контакт: публичный HTTPS URL или `mailto:`. |
| `ENCRYPTION_KEY` | производная от `BETTER_AUTH_SECRET` | Шифрование токенов, секретов webhook, VAPID и shared auth secret push-подписок. |


## Эксплуатация и приватность

`src/instrumentation.ts` запускает два независимых фоновых цикла внутри приложения, вне build/Vitest:
минутную задачу доставки и непрерывный контроллер Telegram. У них разные advisory lock (ключи 1 и 2 в namespace 208476).
Контроллер удерживает отдельную закреплённую SQL-сессию без idle/max-lifetime timeout; при потере сессии polling отменяется,
затем реплики снова выбирают лидера. Сервисные запросы используют обычный пул, поэтому `DB_POOL_MAX=1` поддерживается.
Смена токена, отключение бота или переход на webhook в админке обнаруживаются всеми репликами не позднее следующей
секундной проверки БД: активный long poll и backoff отменяются, старая конфигурация больше не обрабатывает новые ответы.
На SIGTERM/SIGINT активный HTTP-запрос прерывается и SQL-сессия освобождается. Перекрывающиеся минутные тики пропускаются.
`JOBS_ENABLED=false` отключает оба фоновых процесса, но оставляет настройки и webhook endpoint доступными.
Никаких брокеров или отдельных воркеров не требуется. Для DB достаточно обычных прав приложения и поддержки PostgreSQL advisory locks.

Пользователь получает данные только семей, где он остаётся участником с `finance.read`. Блокировка пользователя отключает доставку.
При выходе из семьи её настройки и журнал доставки этого пользователя удаляются по FK.
Системный администратор видит коды ошибок, но не получает доступ к финансам семей через эту страницу.

Telegram получает текст, суммы, названия и chat_id. Служба Web Push получает endpoint и зашифрованное содержимое;
браузер отображает расшифрованный текст, в том числе на экране блокировки. Учитывайте это при включении канала.
В БД сохраняются привязка Telegram, хеш временного токена, endpoint/публичный ключ браузера, зашифрованный shared auth secret и метаданные доставки;
текст финансовых уведомлений в БД и серверные логи не пишется. Журнал апдейтов содержит только ID бота/апдейта.
Удалить привязку и устройства можно в профиле. E-mail-канал в этой версии не добавлен.

Compose передаёт новые переменные из `.env`. Для Helm: `notifications.jobsEnabled`, `notifications.telegram.*`, `notifications.vapid.*`;
при `existingSecret` добавьте в него нужные `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `VAPID_PRIVATE_KEY`.
Публичный ключ и режим остаются в values. Процедуры восстановления и ротации ключа шифрования совпадают с SSO.
