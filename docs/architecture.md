# Архитектура BestBudget

Один веб-сервис на Next.js (App Router) и PostgreSQL. Никакой дополнительной инфраструктуры (очередей, кэшей, воркеров) не требуется.

```text
src/
├── app/                 # маршруты Next.js
│   ├── (auth)/          # вход, первичная настройка, приглашения, регистрация, сброс пароля
│   ├── (app)/           # приложение: обзор, операции, календарь, бюджеты, аналитика, счета, настройки, администрирование
│   ├── actions/         # server actions — тонкий слой: сессия → контекст → сервис → revalidate
│   └── api/             # /api/auth/* (Better Auth), /api/health
├── components/          # UI: ui/ — shadcn/ui (Base UI), app/ — компоненты приложения
├── db/                  # схема Drizzle, клиент, мигратор
├── domain/              # чистая бизнес-логика без I/O: расписания, прогноз, права, справочники
├── lib/                 # деньги, даты, env, шифрование, Better Auth
└── server/              # серверная логика: контекст и проверка прав, сервисы, аудит
drizzle/                 # SQL-миграции
scripts/                 # миграции, CLI администратора, локальная БД (PGlite)
tests/integration/       # интеграционные тесты сервисов на реальной схеме
e2e/                     # Playwright
```

## Слои и изоляция данных

- **Server actions** (`src/app/actions`) получают пользователя из сессии и активное семейное пространство из cookie `bb_household`.
  Членство каждый раз проверяется в БД (`resolveHouseholdCtx`) — подделанная cookie просто не даёт доступа.
- **Сервисы** (`src/server/services`) принимают `HouseholdCtx` и проверяют права (`assertCan`). Каждый запрос к финансовым данным
  содержит `household_id = ctx.householdId`; запись по чужому идентификатору — «не найдена».
- **База данных** дополнительно гарантирует изоляцию составными внешними ключами `(household_id, category_id)`,
  `(household_id, account_id)`: операция не может сослаться на счёт или категорию другой семьи даже при ошибке в коде.
- **Права в семье** — `src/domain/permissions.ts`: участник ведёт операции (включая регулярные), администратор дополнительно управляет
  категориями, счетами, бюджетами и приглашениями, владелец — участниками и настройками пространства.
- **Системный администратор** (`users.role = 'admin'`) управляет пользователями и авторизацией, но видит у пространств только метаданные.
  Имперсонация Better Auth отключена.

## Модель данных

| Таблица | Назначение |
|---|---|
| `users`, `sessions`, `auth_accounts`, `verifications`, `rate_limits` | Better Auth (UUID, admin-плагин: роль, блокировка) |
| `households`, `household_members`, `invitations` | семейные пространства, роли, одноразовые приглашения (хранится только SHA-256 токена) |
| `financial_accounts` | счета: тип, начальный остаток, архив |
| `categories` | категории доходов/расходов: иконка, цвет, архив |
| `transactions` | операции: тип, статус, сумма, дата, счёт(а), категория, автор, версия |
| `recurring_rules` | расписания регулярных операций |
| `exchange_rate_fetches` | подтверждённые диапазоны запросов ЦБ, включая отсутствие публикаций; закрытая история без срока, текущий день с TTL |
| `exchange_rates` | глобальные публичные курсы RUB за 1 единицу валюты: дата, NUMERIC(20,10), источник cbr/manual |
| `category_budgets` | месячные лимиты по категориям |
| `application_settings`, `oidc_provider_settings` | настройки приложения и SSO (секрет зашифрован) |
| `audit_logs` | журнал изменений: кто, когда, что изменилось |

- **Деньги** — `BIGINT` в минорных единицах валюты счёта, в коде — безопасные целые числа (`src/lib/money.ts`). Бюджеты — в базовой валюте семьи.
- **Даты операций** — SQL `date` (календарный день в часовом поясе пространства, по умолчанию Europe/Moscow). «Сегодня» вычисляется
  в часовом поясе пространства.
- **Конкурентные изменения** — у операций, расписаний, счетов и настроек семьи есть `version`; обновление выполняется условием `version = <прочитанная>`, иначе
  пользователь получает сообщение о конфликте. Приглашение принимается под `SELECT … FOR UPDATE`, поэтому токен одноразовый и при гонке.
- **История** — `created_by`/`updated_by`/`updated_at` в строках и `audit_logs` с изменёнными полями.
- **Удаление** — категории и счета с историей удалить нельзя, только архивировать; операции расписания при «удалении» помечаются
  пропущенными.

## Регулярные операции

Расписание (`recurring_rules`) материализуется в обычные строки `transactions` со статусом `planned` на 62 дня вперёд. Строка хранит
`occurrence_date` — исходный слот расписания; уникальный индекс `(recurring_rule_id, occurrence_date)` и `INSERT … ON CONFLICT DO NOTHING`
делают генерацию идемпотентной, а блокировка строки расписания сериализует параллельные запуски и редактирование. Генерация запускается
при открытии обзора, операций и календаря, а также scheduler-ом для семей с включёнными уведомлениями.

Даты дальше горизонта (например, календарь через полгода) рассчитываются «виртуально» из расписания и попадают в прогноз; при действии
с такой датой строка создаётся по требованию.

- **Подтверждение** переводит строку в `posted`, можно указать фактическую сумму и дату — слот расписания не меняется.
- **Перенос / изменение одной** — правка строки; связь с расписанием сохраняется.
- **Изменение всех следующих** — правка расписания с даты `effectiveFrom`: неподтверждённые операции с этой даты пересоздаются,
  подтверждённые остаются как были.
- **Остановка** — дата окончания; неподтверждённые будущие строки удаляются.
- **29–31 число** — если дня нет в месяце, используется последний день месяца; в длинных месяцах расписание возвращается к своему дню
  (`src/domain/recurrence.ts`).
- Создание расписания задним числом не порождает просроченных операций: генерация начинается с даты создания (`generate_from`).

## Валюты и курсы

- Справочник `src/lib/currencies.ts` задаёт поддерживаемые ISO 4217 коды и exponent: JPY/KRW = 0, BHD = 3, остальные = 2.
  Парсинг, ввод, форматирование, графики и CSV учитывают exponent; символ берётся из `Intl.NumberFormat("ru-RU")`.
- Счёт хранит свою валюту. Операция хранит `amount` в её минорных единицах; перевод дополнительно хранит `to_amount` в валюте получателя.
  Для разных валют `to_amount` обязателен; в одной валюте NULL означает ту же сумму. Такие же поля есть у регулярных правил,
  материализованных и виртуальных начислений. В форме автоподставляется курс, сумму зачисления можно изменить; эффективный курс — информационный.
- Валюту счёта с любыми операциями (в том числе плановыми/пропущенными) или расписаниями менять нельзя. Триггеры блокируют строки счетов
  в порядке ID при записи операций/правил и проверяют валюту при её изменении, защищая также гонки и прямой SQL.
- `exchange_rates` — глобальные публичные данные с PK `(currency, date, source)`, без household. Ручные курсы вводит системный администратор,
  поскольку изменение затрагивает все пространства; участник может вручную указать зачисленную сумму перевода без изменения общего курса.
  Ручной курс приоритетнее ЦБ на ту же дату; более поздняя дата важнее источника. RUB всегда равен 1.
- Провайдер `FX_PROVIDER=cbr` использует [XML API ЦБ](https://cbr.ru/development/sxml/): свежий день — `XML_daily.asp`, история —
  `XML_dynamic.asp` одним запросом на валюту за весь нужный диапазон с 14-дневным lookback. CBR-ID редакций валют хранится в коде
  и проверяется по настоящему `XML_daily` в тесте. Windows-1251, Nominal, VunitRate/Value, запятая и экспоненциальная запись поддержаны в обоих парсерах.
  `none` отключает только сеть, сохранённые курсы продолжают действовать.
- Потребность на день D закрывает последний известный курс в `[D−14, D]`; точная строка на выходной не требуется.
  Ответ с другой датой сохраняется под датой публикации, включая будущую; при расчёте на D курс позже D не выбирается.
  Успешно проверенные интервалы хранятся в глобальной `exchange_rate_fetches` вместе с курсами в одной транзакции. Это также отрицательный кеш:
  корректный пустой ответ истории закрывает диапазон и переживает перезапуск процесса. ID и границы ответа валидируются до записи кеша;
  сетевые ошибки/битый XML его не заполняют. Подтверждённые прошлые/текущие дни хранятся бессрочно, ещё не наступившие даты — час. Принудительное обновление в админке обходит кеш.
  Соседние интервалы покрытия объединяются при проверке потребности.
- Две попытки по ≤650 мс, общее сетевое окно расчёта ≤1,3 с, до четырёх валют параллельно; одинаковые запросы объединяются,
  повтор неудачной загрузки — через минуту. При многих валютах недостающие диапазоны могут загружаться при последующих открытиях.
  Кнопка обновления за сегодня загружает свежий снимок, за прошлую дату — выбранную валюту за предшествующие 14 дней.
- Конвертация через RUB выполняется целочисленно (`BigInt`); курс хранится с 10 десятичными знаками. Округление half-up
  (ровно половина — от нуля) до минорной единицы результата, проверено тестами. SQL группирует операции по счёту/дате/типу/статусу/категории
  до конвертации; округление выполняется один раз на такую группу. Для семейного масштаба сервис намеренно читает весь сгруппированный ledger:
  он нужен для текущих остатков и истории прогнозов; существующий индекс `transactions_household_status_date_idx` покрывает `(household_id, status, date)`. Курсы загружаются пакетно, запросов к БД на каждую операцию нет.
- Доходы/расходы факта конвертируются по последнему известному курсу ≤ даты операции (будущая дата — не позднее сегодняшней), плановые —
  по последнему известному на сегодня в часовом поясе семьи. Балансы счетов остаются в собственной валюте; итог переоценивается по текущему курсу.
  Календарь и история баланса переоценивают накопленные остатки на каждый прошедший день, прогноз фиксирует последние известные курсы.
  Курсовая переоценка и разница обмена влияют на баланс, но не считаются доходом/расходом и не расходуют категории/бюджеты.
- Исторические даты публикаций не создают предупреждений. Текущий курс старше 7 дней показывается одной строкой на валюту внутри карточки баланса. При полном отсутствии курса сумма исключается из итогов с явным предупреждением
  «Итоги неполные»; перевод и собственный баланс счёта остаются доступны. Предупреждения общие для дашборда, бюджетов, аналитики и календаря.
- Владелец может менять базовую валюту. Лимиты бюджетов сохраняют целые минорные единицы без автоматического пересчёта — форма предупреждает,
  что лимиты надо проверить и задать заново. Это не требует неявного массового изменения лимитов и работает без доступного курса.
- Миграции аддитивны: существующие RUB-суммы, остатки и валюты не изменяются; nullable `to_amount` сохраняет прежнюю семантику переводов.
  Версии новых редактируемых сущностей получают default 1. Тест обновления применяет миграции поверх заполненной схемы беты.

## Баланс и прогноз

- **Фактический баланс** = сумма начальных остатков счетов + все выполненные операции (доход +, расход −, перевод учитывает фактическое списание и зачисление, возможна разница обмена).
- **Прогноз на день D** (`src/domain/forecast.ts`): для прошедших дней — только факт; начиная с сегодняшнего дня добавляются плановые операции.
  Просроченные плановые операции (дата прошла, но не подтверждены) считаются ожидаемыми и учитываются в прогнозе на сегодня.
- **Доступно после обязательных платежей** = фактический баланс − все запланированные расходы до конца месяца, без учёта ещё не полученных
  доходов. Это консервативная оценка: сколько можно тратить сейчас, даже если зарплата задержится.
- **Кассовый разрыв** — день, на конец которого прогноз отрицательный; подсвечивается в календаре и на обзоре.
- **Аналитика** строится только по выполненным операциям, прогноз показывается отдельным блоком.

## Цели и накопления

- `goals` и `goal_contributions` принадлежат household; ссылки на счёт/цель/регулярное правило защищены композитными FK.
  Просмотр и изменение используют `finance.read`/`finance.write`: owner/admin/member могут вести цели как операции. Роли viewer в текущей схеме нет.
- Цель на активном накопительном счёте получает средства по приоритету (меньшее число первым), затем `sort_order`, затем UUID.
  `allocated_amount` — необязательный потолок в валюте **счёта**. Единственная цель без лимита получает весь баланс. До потолка или суммы цели выделяется текущий остаток,
  оставшиеся деньги идут следующей цели. При снятии/изменении приоритетов распределение пересчитывается; сумма выделений никогда
  не превышает положительный баланс. Это распределение существующего остатка, без создания финансовых операций.
  Неизвестный курс блокирует распределение нижестоящим целям, чтобы не отдать им уже зарезервированные средства.
- Ручные взносы — подписанные суммы в валюте цели, с датой и комментарием. Изъятие/исправление — отрицательный/обратный взнос.
  Они не попадают в баланс семьи, доходы, расходы или бюджеты. Будущие ручные взносы не допускаются.
- Подушка вычисляется динамически: расходы из того же ledger, что используется отчётами, за последние 3/6 **полных** календарных
  месяцев (месяцы без расходов тоже входят в делитель), умноженные на выбранные 1–60 месяцев. Расходы пересчитываются по историческим
  курсам в валюту цели; отсутствие курса даёт неизвестную сумму, а отсутствие расходов — нулевую цель без ложного достижения.
- `src/domain/goals.ts` содержит чистые расчёты: целочисленное распределение, подушку, остаток, процент, месячную потребность,
  дату достижения и статус. Потребность и темп используют длину трёх календарных месяцев; денежные округления выполняются через BigInt.
  Текущий прогресс счёта конвертируется по последнему известному курсу на сегодня в часовом поясе семьи.
- Достижение — вычисляемое состояние: сохранённые active/achieved пересчитываются по фактическому прогрессу, поэтому снятие денег
  снова делает цель активной. Архив выключает участие в распределении и удаляет связанное расписание с неподтверждёнными переводами;
  выполненные переводы и ручные взносы сохраняются. Архивная цель счёта показывает нулевое текущее выделение.
- Тип, счёт и валюта закреплены при создании для сохранения смысла истории; остальное редактируется с обязательной `version`.
  Цель блокирует смену валюты связанного счёта даже без операций. Архивную цель можно восстановить.
- История счёта показывает изменения **выделенного** остатка по датам операций. Она реконструируется при текущем распределении/курсе;
  начальный остаток виден на графике, без фиктивного взноса. Темп — изменение распределённой суммы за последние 3 месяца, делённое на 3;
  курсовая переоценка исключена благодаря одинаковому текущему курсу двух снимков.
- График показывает факт и два независимых сценария: продолжение исторического темпа и плановые операции на счёте (включая
  существующие ручные планы и регулярные правила). Для последних используются `virtualOccurrences` и материализованные записи,
  поэтому изменения/пропуски не дублируются. Темп и планы не складываются. Плановая дата имеет приоритет в оценке срока.
  Прогноз ограничен 10 годами, будущая сумма подушки и курсы фиксируются на сегодня; неизвестная дата не обещает достижение.
- Автопополнение вызывает существующий `createRules` с ежемесячным переводом и концом в срок цели. Недостающий остаток счёта делится на фактическое число
  оставшихся дат выбранного дня месяца (29–31 обрабатывает общий механизм). Правило, материализация и связь с целью создаются атомарно;
  уникальная связь исключает дубликат. Для общей копилки сумма включает недостающее финансирование вышестоящих целей; лимит ниже суммы цели блокирует автоматизацию.
  Суммы обмена фиксируются при создании правила, при подтверждении доступны обычные уточнения. Каждую операцию подтверждает пользователь.
  Изменение суммы/срока цели не переписывает расписание; его можно изменить в операциях либо отключить и настроить заново.
- Автопополнения видны в календаре, ближайших операциях и прогнозе через общий ledger. Внутренний перевод не становится расходом семьи
  и не уменьшает общий остаток (кроме валютной разницы); отдельный кассовый разрыв источника не является семейным разрывом.
- Раздел `/goals`, `/goals/[id]` и виджет обзора (3 приоритетные цели) используют общие компоненты, motion с reduced-motion для прогресса,
  графики на `--chart-*`. Seed: подушка, отпуск с расписанием и ручная цель в USD. Новая миграция аддитивна, существующие суммы не меняются.

## Счета и кредитные карты

Перевод — одна строка с `account_id` и `to_account_id`: со счёта списания уходит сумма, на счёт зачисления приходит `coalesce(to_amount, amount)` в его валюте, в доходы и расходы перевод не попадает. Кредитная карта — счёт с отрицательным остатком (долгом): покупки записываются расходом
с карты (учитываются один раз), погашение — переводом с дебетового счёта. Учёт процентов и графиков погашения — задел на будущее.

## Авторизация

- **Better Auth**: e-mail и пароль (scrypt), сессии в БД в HTTP-only cookie, ограничение частоты попыток (хранится в БД), admin-плагин.
- **OIDC** — generic OAuth-плагин с discovery, PKCE и проверкой ID-токена по JWKS. Конфигурация берётся из окружения (приоритет) или из БД.
  Экземпляр Better Auth пересоздаётся при изменении настроек (проверка не реже раза в 5 секунд), перезапуск не нужен.
- **Регистрация закрыта**: хук создания пользователя разрешает его только при первичной настройке, по действующему приглашению
  (для SSO — по HTTP-only cookie с токеном приглашения), при включённой публичной регистрации или авто-создании SSO-пользователей.
- **Связывание SSO** — только явное, из активной сессии (`disableImplicitLinking`).
- **Защита от потери доступа** — `getAuthMethods()` всегда оставляет хотя бы вход по паролю, если SSO недоступен; отключение пароля требует
  привязанного SSO у самого администратора; `AUTH_FORCE_LOCAL_LOGIN` и CLI — аварийный доступ.

## Уведомления и фоновые задачи

`src/instrumentation.ts` запускает минутный scheduler и независимый непрерывный контроллер Telegram только в Node.js runtime,
вне build/Vitest и при `JOBS_ENABLED != false`.
`src/server/jobs/lock.ts` удерживает `pg_try_advisory_lock` на отдельном соединении на всё время прогона; финансовые сервисы продолжают
работать через обычный пул, включая `DB_POOL_MAX=1`. Перекрывающиеся тики пропускаются. При нескольких репликах работает один scheduler.
Telegram использует другой advisory lock (ключ 2 вместо 1) и закреплённую долгоживущую SQL-сессию без idle/max-lifetime timeout.
`getUpdates(timeout: 30)` повторяется сразу после ответа; ошибки и 409 получают backoff. Проверка версии настроек раз в секунду
отменяет HTTP/backoff при смене токена или режима. SIGTERM/SIGINT отменяют polling и освобождают сессию; её потеря тоже отменяет polling.
Callback подтверждается до финансовых запросов, итоговое сообщение отправляется после проверки прав и версии платежа.

`notification_preferences` связана составным FK с членством `(household_id, user_id)` и удаляется при выходе из семьи.
Job заново разрешает контекст и права; финансовые данные читает через существующие сервисы операций, прогнозов и бюджетов.
Суммы платежей форматируются в валюте счёта списания; прогноз, фактический баланс и расходы бюджета — в базовой валюте семьи.
Подтверждение из Telegram использует привязку личного чата, актуальное членство и версию из кнопки. Обычные операции проходят через `confirmTransaction`, связанный кредитный платёж — целиком через `confirmLoanPayment`.

`notification_deliveries` содержит только ключи событий, канал, статусы и безопасные коды ошибок, без текста сообщения.
Уникальность `(user_id, channel, dedupe_key)` и запись попытки до отправки защищают от повторов после рестарта.
Для Web Push ключ включает устройство. Сводка хранит ключи включённых бюджетных предупреждений: один порог не повторяется каждый день.
Явные временные ошибки повторяются с backoff, максимум четыре попытки. Неопределённый исход отправки не повторяется автоматически:
это сознательный выбор в пользу отсутствия дубликатов, при аварии возможен пропуск уведомления.

Токен Telegram, секрет webhook и приватный VAPID-ключ зашифрованы AES-256-GCM. ENV имеют приоритет.
`telegram_links` хранит хеш одноразового подписанного токена с TTL; `telegram_updates` исключает повторную обработку апдейтов.
`push_subscriptions` хранит browser endpoint, публичный ключ и зашифрованный shared auth secret; допустимы только HTTPS endpoints известных служб браузеров, 404/410 удаляют устройство.
Service worker обрабатывает только push/click, без fetch и offline-кэша. Подробности эксплуатации: [notifications.md](notifications.md).


## Кредиты и состав платежа

`loans` принадлежит семье и ссылается составными FK на счёт-обязательство `financial_accounts.kind = loan`, счёт оплаты и расходную категорию процентов. У кредита один счёт, в валюте счёта оплаты; платежи с конвертацией требуют предварительного перевода на счёт этой валюты. Начальный баланс обязательства отрицательный: `−tracking_balance`. `principal` — исходная сумма, `tracking_date` и `tracking_balance` позволяют начать учёт с середины кредита, `term_months` — оставшийся срок, `first_payment_date` — ближайший платёж. При известном аннуитетном платеже срок оценивается целочисленным месячным расчётом; предпросмотр показывает фактический результат выбранного метода. Исторические проценты до начала учёта неизвестны и в переплату не входят.

`src/domain/loan.ts` — чистый расчёт без I/O. Все денежные результаты — целые минорные единицы; ставка хранится decimal-строкой до 6 знаков. Формула аннуитета и начисление процентов используют рациональную арифметику `BigInt`, округление half-up на платёжный период. Последний платёж закрывает остаток точно. Для `monthly` используется r/12; события внутри месяца делят его пропорционально дням. Для `daily_365` каждый день имеет базу 365, для `daily_actual` — 365/366 своего года, включая переход Нового года. Интервал начисления `(предыдущая дата, дата платежа]`, события действуют после своего дня; на дату платежа сначала выполняется плановый платёж, затем событие. При дневном начислении базовый аннуитет считается по r/12, последний платёж уточняется. Сокращённый досрочкой срок фиксируется с учётом уже начисленных процентов: последующая смена ставки или уменьшение платежа сохраняет новую дату погашения. Переносов по выходным, страховок, комиссий, каникул и возобновляемого лимита здесь нет; `credit_line` — вручную заданный график, не модель минимального платежа кредитной карты.

Плановый платёж — две строки `transactions` с общим `loan_payment_key`: перевод тела со счёта оплаты на обязательство и расход процентов со счёта оплаты в «Проценты по кредитам». Нулевые части не создаются (совместимость с `amount > 0`). Уникальность `(loan_id, loan_due_date, loan_part)` и блокировка строки кредита обеспечивают идемпотентность и сериализацию подтверждений/пересчётов. Материализация — 62 дня; дальше вычисляются виртуальные строки для календаря и прогноза. UI объединяет части в одну строку, CSV сохраняет исходные проводки, поэтому тело никогда не превращается во второй расход.

Участник подтверждает обе части одной транзакцией БД (`finance.write`), указывая фактическую сумму и дату. Разница меняет тело или проценты, либо задаётся ручная разбивка. Изменение тела пересчитывает остаток графика с прежним платежом; фактическая проводка относится к фактической дате, расчётная разбивка закреплена за исходным слотом `loan_due_date`. Для фактической досрочки между слотами используется отдельное событие. Подтверждения идут по порядку; нельзя менять отдельную часть или проводить ручную операцию по обязательству через общий CRUD. Создание и события кредита доступны owner/admin через отдельное разрешение `loans.manage`, поскольку меняют структуру обязательств и начальные остатки (тот же уровень, что `catalog.manage`). В текущем приложении роли viewer нет; существующие роли не расширяются этим PR.

`loan_events` расширяем по типу: досрочное погашение (только тело, reduce_term/reduce_payment), смена ставки, сверка основного долга. События записываются хронологически, не позже сегодня, по одному на дату. Досрочка ограничивается фактическим остатком, проводит перевод и оставляет начисленные до неё проценты в следующем платеже. Перед досрочкой/сменой ставки требуются подтверждения предыдущих платежей. Сверка может закрыть неподтверждённые прошлые слоты как сверенные: `balance_delta` — отдельная датированная корректировка обязательства, учитываемая в балансе и историческом прогнозе, без дохода/расхода. Новый график строится от проверенного остатка. Будущие нетронутые planned-строки пересоздаются; posted, skipped и целиком платежи с `version > 1` сохраняются. Закрытие требует нулевого долга и подтверждения оставшихся процентов; удаление разрешено лишь без фактических проводок. История закрытого кредита остаётся.

Ликвидный баланс и прогноз исключают loan-счета: списание тела уменьшает доступные деньги целиком, а не компенсируется зачислением на обязательство. Чистые активы включают все положительные и отрицательные остатки по актуальным курсам в базовой валюте семьи. Накопительные счета целей остаются активами; распределение между целями и ручные взносы не добавляют остатки повторно. Счета `loan` исключены из выбора накопительного счёта и источника пополнения цели. Автопополнение цели — обычный перевод между активами, поэтому сохраняет общий баланс; кредитный платёж уменьшает его на тело и проценты. Оба расписания вместе учитываются календарём и прогнозом, включая виртуальные вхождения после 62 дней. Долги — сумма отрицательных остатков, включая кредитные карты/овердрафты. Отчёты по расходам учитывают только проценты, свободные деньги после обязательств — и тело, и проценты. Кредитный лимит (`credit_limit`, безопасный default 0 для беты) не актив; доступно по карте = max(0, лимит + баланс).

Миграция `0006_loan_schedules` сгенерирована поверх `0005_savings_goals`: таблицы целей и связь автопополнения сохранены; ручных SQL-дополнений нет. Интеграционная проверка обновления беты включает существующую цель и связанное правило.
## Импорт выписок

`/transactions/import` → выделенный `POST /api/import` (Origin, сессия, ограниченный поток до 10 МБ) → чтение CSV/XLSX → профиль/мастер → нормализация → `imports.previewImport` → черновик → решения → `imports.commitImport`. Общий лимит server actions не увеличен; маршрут также принимает большой пакет решений. Отмена и создание правил доступны через `runAction` server actions.

- `import_batches`: семья, счёт по умолчанию для строк без подсказки, профиль/версия, SHA-256, период, настройки, счётчики, статус `draft/committed/undone`, автор и версия.
- `import_rows`: позиция в исходнике, нормализованные денежные/датовые поля и raw-описание, счёт/категория, кандидаты/решение, fingerprint, эффект, версия и обратная ссылка на операцию. Две стороны перевода ссылаются на одну `transactions`. До подтверждения плановой/преобразования ручной операции сохраняется снимок её финансовых полей для отмены.
- `import_profiles`: новые именованные настройки чтения/колонок семьи. Профили не изменяются на месте; новая конфигурация сохраняется с новым именем.
- `category_rules`: подстрока или RE2 regex описания, MCC, валюта, диапазон модуля суммы, приоритет, категория, версия. Условия через «и»; пользовательские правила выше встроенного MCC и подсказок банка.

Внешние ключи к партиям, счетам, категориям и операциям составные `(household_id, id)`. Новая уникальность `(household_id, id)` на `transactions` аддитивна и не меняет существующие данные. В новой миграции этот ключ создаётся перед внешним ключом входящих строк. Старые миграции не изменены.

Коммит/отмена блокируют строку household и затем партию; все изменения и аудит проходят в одной транзакции БД через сервисы операций с переданным `DbOrTx`. Повтор одного коммита возвращает сохранённые счётчики. Стабильный внешний ID имеет отдельный хешированный ключ области `source + account + external_id`, уникальный по семье среди действующих импортированных строк. Fingerprint **не уникален**: при пересечении файлов каждая прежняя строка поглощает только одно совпадение. После ожидания блокировки совпадения перепроверяются; устаревший предпросмотр не создаёт дубли молча. Ручные совпадения предлагаются по сумме/счёту ±2 дня, плановые — по сумме с допуском и окну дат; неоднозначные планы требуют выбора.

Отмена сначала проверяет все затронутые версии и связи с другими партиями, затем удаляет только созданные операции или восстанавливает прежние финансовые поля. Версии монотонны; конфликт отклоняет всю отмену. Обычное ручное удаление операции отсоединяет её import-ссылки в той же транзакции; последующая отмена сообщает об удалении. Стороны перевода сохраняют собственные исходные даты в provenance, итоговый перевод использует день списания.

CSV-парсер поддерживает кавычки/переносы, BOM, строгий UTF-8 и явный Windows-1251; суммы преобразуются через целые `BigInt` в допустимые минорные единицы. `read-excel-file` 9.x выбран как поддерживаемый reader-only XLSX-парсер с SAX XML, системами дат 1900/1904 и `parseNumber` для сохранения исходных чисел строками. `fflate` (также зависимость reader) предварительно потоково проверяет **реальный** распакованный объём, пути, координаты и запрещённые XML/части до чтения книги; лимиты 40 МБ / 1000 записей. `re2js` обеспечивает ограниченный линейным временем язык пользовательских regex, без нативного toolchain и backtracking. Эти зависимости используются только на серверном пути.

Оригинал файла не сохраняется даже у черновика; нормализованные строки остаются в истории. Описания/условия правил не включаются в обычные логи и аудит импортера. Собственный CSV v1 и экспорт BestBudget поддерживаются, Т-Банк — явно экспериментальный исторический кандидат. [Пользовательская инструкция и границы](import.md).

Предпросмотр импорта отделяет решения к записи от чекбоксов массового редактирования; клиентские итоги исключают пропуски, связи и выбранные переводы. Тип плановой операции передаётся в метаданных кандидата. Миграция импорта `0007_statement_import` следует за кредитами. Совпадения с полной суммой составного кредитного платежа или его частями блокируются в предпросмотре и при записи старого черновика: подтверждение выполняется в разделе «Кредиты», без раздельного изменения тела и процентов. Плановые переводы целей продолжают подтверждаться как одна операция с двумя строками происхождения.
