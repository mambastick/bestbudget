# BestBudget на главном экране

BestBudget устанавливается как PWA и запускается в отдельном окне без адресной строки. Требуется **HTTPS** с доверенным сертификатом. Исключение для разработки — `http://localhost`; HTTP по LAN-адресу телефона недостаточно. В `APP_URL` задайте тот же HTTPS origin, который открывают пользователи, включая порт при необходимости. Настройка reverse proxy — в [SSO](sso.md).

## Установка

- **iPhone/iPad, Safari:** откройте BestBudget → «Поделиться» (в новых версиях Safari может находиться в меню страницы) → «На экран “Домой”» → «Добавить». Если есть переключатель «Открывать как веб-приложение», оставьте его включённым. Запускайте с появившейся иконки.
- **Chrome/Edge и другие браузеры на iOS 16.4+:** браузер может предоставлять «На экран “Домой”» в меню «Поделиться». Если пункта нет, откройте тот же URL в Safari. Поддержка зависит от браузера. [WebKit о сторонних браузерах](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
- **Android, Chrome/Edge:** меню пользователя BestBudget → «Установить приложение» либо меню браузера → «Установить приложение» / «Добавить на главный экран». Системный диалог появится, когда браузер разрешит установку; иначе BestBudget покажет инструкцию.
- **Компьютер, Chrome/Edge:** кнопка в меню пользователя или профиле, значок установки у адресной строки либо меню браузера. **Safari на Mac:** «Файл → Добавить в Dock».

Кнопка также есть в «Настройки → Профиль и безопасность». В standalone-окне она скрыта. Установка не запрашивает разрешение на уведомления. Push включается отдельно в профиле; на iOS/iPadOS нужен установленный PWA и версия системы **16.4+**. [Ограничения Web Push от Apple](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

Долгое нажатие на иконку в поддерживающих браузерах даёт «Новую операцию», «Календарь» и «Импорт выписки». `/dashboard?new=transaction` открывает обычный диалог операции и сразу убирает параметр из URL, чтобы не открывать его повторно.

## Вход и сессия

Установленное приложение на iOS имеет собственное хранилище. Обычно достаточно один раз войти **внутри приложения**. Начиная с iOS/iPadOS 17.2 браузер копирует cookie при установке, поэтому уже выполненный вход может перенестись. Затем cookie и остальные данные браузера и PWA независимы; localStorage не копируется. Выход в Safari не означает выход из уже установленного приложения. [WebKit о переносе cookie](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).

Better Auth в `src/lib/auth.ts`: `expiresIn = 30 дней`, `updateAge = 1 день`. Используемая сессия продлевается до текущего времени + 30 дней не чаще раза в сутки. Клиентский `authClient.useSession()` в каркасе обращается к auth endpoint, где можно установить обновлённую cookie; одних чтений из Server Components для этого недостаточно. Без использования 30 дней, после отзыва сессии, очистки данных браузером или сброса пароля потребуется вход заново. Срок не увеличен ради PWA.

OIDC запускается существующим Better Auth клиентом в текущем окне, без `target="_blank"` и popup. Redirect URI: `APP_URL/api/auth/callback/oidc`; после callback — относительный `/dashboard` (при привязке аккаунта — `/settings?tab=profile`). Эти пути входят в manifest `scope: "/"`. Не заменяйте публичный `APP_URL` внутренним адресом сервера и не расширяйте scope на домен IdP. HTTPS, PKCE, state и проверки origin сохраняются.

Переход на внешний IdP находится вне scope. То, как iOS отображает окно аутентификации и возвращает управление, зависит от WebKit, версии ОС и цепочки редиректов конкретного IdP. Нельзя программно гарантировать передачу уже открытой вкладки Safari в установленный PWA. E2E с mock IdP проверяет callback в том же контексте с флагом standalone; это **не доказательство поведения реального iPhone**. При зависании в браузере вернитесь к иконке приложения и повторите вход оттуда; проверьте `APP_URL`, redirect URI и отсутствие дополнительных переходов на другой origin. Реальный SSO на iOS входит в обязательную проверку перед приёмкой.

## Офлайн и обновления

SW глобально регистрируется после загрузки страницы, только в production и secure context. В Cache Storage попадают **только** два публичных HTML-экрана `/offline/ru`, `/offline/en` и PNG-иконки 192/512 (включая maskable). Финансовые страницы, RSC, API, cookie, суммы, операции и JS-код приложения SW **не кеширует**. Это не офлайн-бухгалтерия. Уже отображённые данные остаются в памяти открытого окна; новые данные и изменения требуют соединения.

Документные навигации идут в сеть с `cache: "no-store"`. При сетевой ошибке SW показывает «Нет соединения · Повторить»; обычный HTTP-ответ сервера, включая ошибку сервера, сохраняет своё значение. Офлайн-переход по внутренней ссылке переводится из Next.js client navigation в документную, чтобы SW мог показать заглушку. «Повторить» загружает исходный URL. Офлайн-экран работает без React/Next.js, использует последний язык приложения и тему устройства из localStorage. В закрытом хранилище — язык браузера/системная тема. Без первой успешной загрузки и установки SW заглушка недоступна.

Новая production-сборка меняет статический `/sw-version.js`, импортируемый SW. Идентификатор един для всех реплик одного build; `updateViaCache: "none"` исключает устаревший импорт. Cache name включает идентификатор. Старые кеши **только с префиксом BestBudget** удаляются при активации. Иные кеши origin не затрагиваются.

Новый worker ждёт; тост «Доступна новая версия — Обновить» предлагает закончить ввод. Только нажатие отправляет `SKIP_WAITING` и перезагружает эту вкладку. Другие открытые вкладки получают предложение обновиться и сохраняют формы. Проверка обновления происходит при загрузке и возвращении в окно (не чаще раза в час). Без открытых старых окон браузер активирует обновление сам.

## Внешний вид

Ориентация `any`: телефон может оставаться в портретном режиме, планшеты и desktop не блокируются. `id: "/dashboard"` совпадает с прежним неявным ID из `start_url`, чтобы не создавать вторую установку. Manifest использует светлые цвета запуска; живой `<meta name="theme-color">` синхронизируется с фактически выбранной темой приложения, включая ручную смену и system.

`black-translucent` на iOS даёт приложению рисовать фон под статус-баром; шапка, боковая панель, FAB и footer диалогов учитывают `safe-area-inset-*`. Шрифт полей на мобильном не меньше 16px, пользовательский zoom разрешён. Overscroll отключён у корня; прокрутка содержимого и выделение финансового текста остаются доступны. У вложенных страниц есть «Назад» к родительскому разделу, в том числе при открытии прямой ссылки.

`apple-touch-startup-image` с media queries покрывает основные iPhone/iPad в обеих ориентациях и темах. PNG генерируются `ImageResponse` через `/pwa-splash` с ограниченным набором размеров. iOS выбирает стартовую картинку по **системной** теме, не по localStorage приложения; при противоположной ручной теме переход цвета полностью исключить нельзя. Новые/неподдержанные размеры и кеширование splash самой ОС проверяются на устройстве.

## Воспроизводимые проверки

`e2e/pwa.spec.ts` работает с отдельным синтетическим пользователем/seed-demo, production artifact и изолированной БД (3200/54330). Проверяет manifest, иконки, screenshots, splash allowlist, глобальный SW без push permission, состав кеша, офлайн на ru/en, повторную загрузку, shortcut, install prompt и его fallback, скрытие установки в standalone, сохранение ввода при обновлении (две вкладки), safe areas и темы на мобильном viewport.

`public/screenshots/` содержит изображения **только seed-demo** для расширенного окна установки Android. `docs/screenshots/pwa/` — состояния iPhone-эмуляции: светлая/тёмная тема, диалог, боковая панель, инструкции Safari/Chrome. Chromium не эмулирует настоящий iOS status bar/вырез; тест подставляет `47px/34px` в CSS-переменные, которые в приложении читают `env(safe-area-inset-*)`. Флаг `navigator.standalone` проверяет логику, но не заменяет WebKit.

На реальном устройстве владелец проверяет:

1. Установку Safari и Chrome iOS/Android, запуск с иконки без browser chrome; desktop Chrome/Edge.
2. Вырез, статус-бар в обеих темах, home indicator, экранную клавиатуру, прокрутку длинного диалога; iPad landscape.
3. Холодный запуск и splash при светлой/тёмной системной теме, включая ручную противоположную тему приложения.
4. Локальный вход, закрытие/повторный запуск, OIDC с реальным IdP и возврат в PWA, продление сессии спустя сутки.
5. Авиарежим → переход → заглушку → восстановление связи → «Повторить»; push после отдельного разрешения (iOS 16.4+).
6. Обновление при открытой незавершённой форме, в том числе в двух окнах: перезагрузка только после согласия.
