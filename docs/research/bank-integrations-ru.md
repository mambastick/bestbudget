# Сбер, Т-Банк и Альфа-Банк: интеграции для семейного BestBudget

Дата проверки открытых источников: **23.10.2026**. Условия задачи: физлица, отдельная self-hosted установка у каждой семьи, нет юридического лица — агрегатора, бюджет на сервисы — 0 ₽. Это исследование, а не реализованные интеграции.

## Краткий вывод

**Сейчас: импорт файлов и ручной учёт кредитов.** Бесплатный публичный API всех счетов, операций и кредитных графиков для отдельной семьи не подтверждён.

- **Сбер:** Sber API предоставляет выписки организаций. Подключение домашнего BestBudget к розничному обмену не подтверждено. [Каталог](https://developers.sber.ru/portal/products/sber-api).
- **Т-Банк:** T-API требует ООО/ИП и Т-Бизнес; T-Invest API обслуживает инвестиции. [T-API](https://developer.tbank.ru/docs/api/t-api), [T-Invest](https://developer.tbank.ru/invest/intro/intro/token).
- **Альфа:** API данных **физлиц существует**, но партнёр по договору — юрлицо/ИП, налоговый резидент РФ. [Каталог](https://developers.alfabank.ru/), [договор, п. 1.11](https://alfabank.servicecdn.ru/site-presets/c6/1f/3211/Dogovor_Alfa_API_27042026.pdf).
- **Open Banking:** 01.10.2026 — дата рекомендательных стандартов; обязательный доступ для семейного приложения с конкретной даты не установлен. [СТО БР, раздел 3](https://www.cbr.ru/Content/Document/File/185555/20251219_od_2887_1.pdf).
- **План:** универсальный CSV → банковские адаптеры по обезличенным образцам → PDF → необязательные Android-черновики. Почта и чеки дополняют выписки. Скрейпинг не делать; API повторно исследовать через 6–12 месяцев.

Точная степень подтверждения форматов и синтетические примеры находятся в [statement-formats.md](statement-formats.md). Ни один нативный парсер банка пока не прошёл приёмку на настоящей выгрузке.

## Как читать результаты

Метки относятся к утверждениям, а не к качеству продукта банка:

- **[П]** — подтверждено первоисточником: банк, ЦБ, ФНС, опубликованный текст закона либо документация владельца инструмента. Это подтверждение документа, не проверка в авторизованном ЛК.
- **[П-ист]** — первоисточник исторический; наличие документа проверено сегодня, актуальность функции в интерфейсе 2026 года не доказана.
- **[В]** — вывод исследования или проектная рекомендация BestBudget.
- **[Н]** — не установлено; нельзя превращать в обещание или жёсткую схему парсера.
- **[С]** — вторичное свидетельство, явно отделённое от банковского контракта.

Все приведённые ссылки проверялись 23.10.2026; дата публикации источника может быть существенно старше. Часть сайтов возвращает защитную страницу/тайм-аут: где использована только индексированная официальная справка, это отмечено. Банковские логины, SMS-коды, токены и персональные выписки не запрашивались. Подключение API, отправка реальных уведомлений, IMAP и выгрузка из банков **не тестировались**.

## 1. Официальные интерфейсы: что доступно и кому

### 1.1 Матрица для нашего сценария

«Не найден» ниже означает отсутствие подтверждённого публичного self-service пути в изученных источниках, а не доказательство отсутствия закрытого партнёрского API.

| Банк / интерфейс | Счета и баланс физлица | Карты и операции физлица | Кредиты: остаток / график | Доступ отдельной семьи за 0 ₽ |
|---|---|---|---|---|
| Сбер, публичный Sber API | Выписки **организаций** [П] | Бизнес-карты и операции организаций [П] | Бизнес-кредитные сценарии; личный долг/график не подтверждены [Н] | Подходящий путь не найден [В] |
| Сбер, межбанковский обмен | Работающие клиентские сценарии есть [П] | Набор зависит от банковской связки [П] | Полный розничный кредитный API для BestBudget не подтверждён [Н] | Не найден публичный onboarding домашнего сервера [Н] |
| Т-Банк, T-API | Счета бизнеса [П] | Выписки бизнеса [П] | Кредитные продукты бизнеса [П] | Нужны ООО/ИП и Т-Бизнес [П] |
| Т-Банк, T-Invest API | Инвестиционные счета/портфель [П] | Биржевые операции, не покупки по Black [В] | Не API бытовых кредитов [В] | Токен инвестору доступен; задачу не решает [В] |
| Альфа, Alfa API: счета ФЛ | Каталог заявляет дебетовые счета, баланс, реквизиты [П] | Из этой карточки нельзя вывести доступность всей карточной истории [Н] | Полный долг и график в данном продукте не подтверждены [Н] | Партнёр — юрлицо/ИП по договору [П] |
| Альфа, выписки ЮЛ | Счета компаний [П] | JSON/1С/MT940 и др. для ЮЛ [П] | Не доказательство розничного кредитного API [В] | Не подходит семье [В] |

Основания матрицы: [каталог Sber API](https://developers.sber.ru/portal/products/sber-api), [справочник его методов](https://developers.sber.ru/docs/ru/sber-api/specifications/overview), [T-API: начало работы](https://developer.tbank.ru/docs/api/t-api), [T-Invest: токены](https://developer.tbank.ru/invest/intro/intro/token), [Alfa: каталог](https://developers.alfabank.ru/), [Alfa: договор 27.04.2026](https://alfabank.servicecdn.ru/site-presets/c6/1f/3211/Dogovor_Alfa_API_27042026.pdf).

### 1.2 Сбер

**[П]** В каталоге Sber API получение операций прямо относится к счетам организаций; вход по Сбер ID и СберБизнес ID — отдельные продукты. Название «Сбер ID» само по себе не даёт разрешения читать счета. Бизнес-API также содержит платежи, бизнес-карты и кредитные предложения. [Описание продукта](https://developers.sber.ru/portal/products/sber-api), [справочник](https://developers.sber.ru/docs/ru/sber-api/specifications/overview).

**[П]** Документация печатной выписки Sber API, обновлённая 19.10.2026, перечисляет PDF, EXCEL, DOCX, RTF. **[В]** Эти форматы нельзя приписывать розничному СберБанк Онлайн: это другой канал и договор. Старое имя SberBusiness API также не обозначает личный open banking. [Метод печатной выписки](https://developers.sber.ru/docs/ru/sber-api/specifications/statement/statement-print).

**[Н]** Не установлен публичный способ выдать произвольному домашнему серверу отдельное от банка право чтения личных счетов, карт, истории, остатка потребкредита и его будущих платежей. **[В]** В BestBudget не предлагать поле для пароля СберБанк Онлайн и не использовать внутренние endpoints мобильного банка как «официальный API».

### 1.3 Т-Банк

**[П]** T-API предлагает прямую и партнёрскую интеграции, выписки, платежи, кредитные продукты; для начала нужны ООО/ИП и доступ к Т-Бизнесу. Бесплатность API не отменяет ограничений по клиенту и виду счёта. [Документация](https://developer.tbank.ru/docs/api/t-api), [продукт Т-Бизнеса](https://www.tbank.ru/business/open-api/).

**[П]** T-Invest API позволяет выпускать токены, в том числе read-only, для информации об инвестициях. **[В]** Это возможный отдельный будущий коннектор инвестиций, а не обход отсутствия API текущих счетов. [Документация токенов](https://developer.tbank.ru/invest/intro/intro/token).

**[П-ист]** В ответе команды банка на вопрос про self-service счета физлица в 2020 году говорилось об ограниченном партнёрском доступе без информации о счетах и оплатах. **[В]** Это объясняет историческое ограничение, но не служит самостоятельным доказательством ситуации 2026 года. Текущий вывод основан на нынешних условиях T-API и отсутствии найденного розничного onboarding. [Обсуждение в репозитории банка](https://github.com/Tinkoff/business-openapi/issues/12).

**[Н]** Бесплатный публичный банковский токен для всех личных карт/операций и полного графика потребкредита не найден. Показ долга в банковском приложении не означает существование API для третьей стороны.

### 1.4 Альфа-Банк

**[П]** В developer-каталоге отдельно представлены выписки ЮЛ и информация о дебетовых счетах ФЛ. У последней заявлены список счетов, баланс, реквизиты. **[Н]** Каталог не подтверждает полный набор операций по картам, кредитные остатки и расписание погашения. При прямом чтении портал временами блокирует запрос; сведения о продукте доступны в поисковом индексе официального сайта. [Каталог Alfa API](https://developers.alfabank.ru/).

**[П]** В опубликованном договоре версии 6 от 27.04.2026 клиентом может быть физлицо, но партнёром API — только юрлицо или ИП — налоговый резидент РФ (пп. 1.9, 1.11, 2.3.1). **[В]** «Данные физлица» и «право физлица подключить приложение» — разные условия. Не нужно предполагать отдельную банковскую лицензию там, где договор требует конкретный статус партнёра. [Договор Alfa API](https://alfabank.servicecdn.ru/site-presets/c6/1f/3211/Dogovor_Alfa_API_27042026.pdf).

**[В]** При изменении модели проекта можно запросить условия такого партнёрства; сейчас оно не укладывается в заданную модель. Нельзя распространять один partner secret в исходниках и считать каждую семейную установку одобренным банком клиентом. Alfa ID для входа также не гарантирует разрешения на банковские данные.

### 2.2 Какие данные описаны стандартами

**[П]** В правилах получения информации о счетах, раздел 6.1, предусмотрены данные счёта, баланс и операции ФЛ. Карты и связанные финансовые продукты для ФЛ отмечены как опциональные. Информация о кредитных лимитах может передаваться как тип баланса. [Правила взаимодействия, с. 12–13](https://www.cbr.ru/Content/Document/File/185567/20251219_od_2891.pdf).

**[П]** Спецификация ФЛ содержит ресурсы счетов, остатков, карт, продуктов и транзакций. В типах продуктов встречаются кредиты, но краткие сведения о продукте и кредитной линии не равны полному реестру обязательств с графиком, процентами, просрочкой и суммой досрочного закрытия. **[В]** Нельзя обещать кредитный импорт по одному наличию `/products`; необходимы отдельная схема и подтверждение её реализации конкретным банком. [Методы ФЛ, разделы 11, 13.2.4, 13.3.16, 14.2](https://www.cbr.ru/Content/Document/File/185573/20251219_od_2894.pdf).

### 2.3 Кто получает данные, реестры и ИБ

**[П]** ЦБ описывает обмен между **организациями**, отвечающими критериям участников. Согласие клиента необходимо; на странице проекта Платформа коммерческих согласий на Госуслугах всё ещё обозначена как пилотируемая (страница обновлена 24.12.2025). **[Н]** Это не доказывает отсутствие более позднего запуска ПКС, но общедоступный путь подключения семейного BestBudget не подтверждает. [FAQ ЦБ](https://www.cbr.ru/fintech/api/).

**[П]** Принципы 2024 года предусматривают требования к участникам и реестр под надзором ЦБ. Правила 2025 года требуют сообщать пользователю сведения об организации в реестре среды и её допуске как СПУ. **[Н]** Общедоступная завершённая процедура «зарегистрировать домашнее приложение физлица», цена допуска и исчерпывающий действующий список требований не установлены. [Принципы, раздел 2.1](https://www.cbr.ru/Content/Document/File/165674/document_2024-09-02.pdf), [Правила, раздел 5.1](https://www.cbr.ru/Content/Document/File/185567/20251219_od_2891.pdf).

**[П-ист]** Ранняя концепция АФТ описывала аккредитацию и публичный реестр, с ещё подлежащими определению критериями. **[В]** Нельзя выдавать этот замысел за действующий порядок аккредитации 2026 года или переносить европейскую PSD2/AISP-лицензию на РФ. [Концепция АФТ, с. 12](https://openbankingrussia.ru/upload/iblock/460/dmr7my2an0pkdpd10xzytif0u0vzvcuu/%D0%9A%D0%BE%D0%BD%D1%86%D0%B5%D0%BF%D1%86%D0%B8%D1%8F%20%D0%BE%D1%82%D0%BA%D1%80%D1%8B%D1%82%D1%8B%D1%85%20API.pdf).

**[П]** Комплекс включает ФАПИ.СЕК, ФАПИ.ПАОК, профили расширенной безопасности: OAuth/OIDC, проверку подписанных сообщений и сертификатов/ключей участников. **[В]** Это институциональное доверие, а не просто REST с личным bearer-токеном. Self-hosted серверу потребуются одобренная идентичность клиента, регистрация адресов возврата и ключей, безопасное хранение и отзыв согласий согласно конкретному соглашению. HTTPS и OAuth-библиотека сами по себе допуска не обеспечивают. [Список стандартов](https://www.cbr.ru/fintech/api/prikladnye-standarty/), [профили безопасности](https://www.cbr.ru/Content/Document/File/185561/20251219_od_2888.pdf).

**[В] Реалистичность для нас:** на существующих условиях низкая: нет подтверждённого допуска обычной семьи, бесплатного onboarding каждого инстанса и договорной модели. Это организационный барьер даже при наличии компетенций реализовать API. Согласие на обработку данных в BestBudget не заменяет согласия в банке и одобрения получателя.

### 2.4 Что работает на практике

**[П]** АФТ разрабатывает стандарты совместно с рынком и передаёт их ЦБ. В сообщении 25.09.2025 она подтверждает продуктивный обмен данными по счетам между крупными банками и план перехода на новые версии 01.10.2026. **[В]** Это свидетельство работающего обмена, не всеобщего допуска сторонних разработчиков. [Сообщение АФТ](https://www.fintechru.org/press-center/news/ekspertnyy-sovet-assotsiatsii-fintekh-soglasoval-paket-novykh-standartov-otkrytykh-api-dlya-finansov/).

**[П]** ЦБ сообщает об испытаниях с реальными клиентами с 2024 года и возможности видеть продукты разных банков в одном банковском интерфейсе. **[П]** Т-Банк в своей актуальной продуктовой статье описывает добавление чужих счетов, просмотр операций, погашение кредитов; это описание клиентского интерфейса, не опубликованный партнёрский API графиков. [Сообщение ЦБ](https://www.cbr.ru/press/event/?id=28214), [новое приложение Т-Банка](https://www.tbank.ru/finance/blog/new-mb/).

**[В] Проектирование:** пользователь сам включает доставку в банке; BestBudget читает выделенный ящик/папку через IMAP over TLS. Приложению не нужен пароль банка, но нужен ограниченный почтовый токен/пароль приложения. Локально хранить его зашифрованным, маскировать в логах, уметь отключать. Не выдавать доступ ко всему семейному ящику без необходимости.

Имя отправителя не доказывает подлинность: фильтровать домен и проверенные почтовым сервером результаты SPF/DKIM/DMARC, не доверять произвольному заголовку Authentication-Results извне. Не открывать ссылки автоматически, не исполнять HTML/макросы, вложения обрабатывать с лимитами. Письмо должно попадать в тот же предпросмотр, что файл.

**[П]** Tasker поддерживает HTTP Request с заголовками и телом. У него семидневная пробная версия, затем покупка: при строгом нулевом бюджете рассчитывать на него нельзя, если лицензии уже нет. [HTTP Request](https://tasker.joaoapps.com/userguide/en/help/ah_http_request.html), [FAQ оплаты](https://tasker.joaoapps.com/faq-ov.html).

**[В]** В MacroDroid эквивалентная связка — событие SMS/Notification → фильтр → действие HTTP Request, а не входящий Webhook Trigger. **[Н]** Актуальные бесплатные лимиты и настройки 2026 года не подтверждены: Wiki возвращает 403; валидировать на телефоне. Не обещать «пять бесплатных макросов» по старым обзорам. [Страница действия в Wiki](https://macrodroidforum.com/wiki/index.php/Action:_HTTP_Request).

**[П]** Т-Банк описывает оповещения об операциях и их настройки; Альфа — SMS/push «Альфа-Чек», с платностью в розничном предложении. **[В]** «Бесплатный webhook» не означает бесплатный банковский источник; push также может входить в платную услугу. Точные тарифы семьи надо проверить до выбора канала, новые платные опции при бюджете 0 не подключать. [Т-Банк: оповещения](https://www.tbank.ru/cards/debit-cards/tinkoff-black/), [Альфа: условия розничного предложения](https://alfabank.ru/lp/newdebet/).

### 5.2 Тексты трёх банков: ограничения и примеры

**[Н]** Стабильная опубликованная банками грамматика SMS/push на 2026 год не найдена. Отправитель, маска карты, порядок суммы, остатка, даты и магазина могут меняться. Следующие тексты **полностью синтетические учебные варианты**, не копии сообщений и не подтверждённые шаблоны банков:

| Предполагаемый банк | Синтетический текст расхода | Что пробовать извлечь |
|---|---|---|
| Сбер | `VISA1234 22.10.26 18:20 Покупка 450р MAGAZIN PRIMER Баланс: 9550р` | `1234`, локальное время, 450 RUB, покупка; 9550 — остаток, не сумма операции |
| Т-Банк | `Покупка 450 ₽. Карта *5678. MAGAZIN PRIMER. Доступно 9 550 ₽` | `5678`, 450 RUB, торговое описание; время отсутствует |
| Альфа | `Покупка: 450.00 RUR. Карта *9012. MAGAZIN PRIMER. Доступно: 9550.00 RUR` | `9012`, 450 RUB; `RUR` нормализовать только по явному профилю |

**[В]** Аналогично нужны реальные обезличенные варианты `Зачисление/Пополнение/Перевод/Возврат/Отмена`, комиссия, снятие и кредитный платёж. Без них распознавание входящих денег нельзя считать проверенным. Слова «перевод» недостаточно для определения направления; число после «Доступно» не является доходом. Код подтверждения может содержать сумму и слово «покупка» — такие сообщения нельзя отправлять на сервер.

### 5.3 Минимально приемлемая схема

Все пункты ниже — **[В] требования к будущей реализации**, а не уже существующие endpoints:

1. Только Android владельца. Разрешения SMS и Notification Access пользователь выдаёт явно. Проверить конкретную версию ОС, пакет банка и ограничения фонового запуска/энергосбережения; обещать аналогичную фоновую схему на iOS нельзя.
2. На телефоне — разрешающий список пакетов/отправителей и **дополнительный запрет** OTP, входа, подтверждения, PIN/CVV, реквизитов авторизации. Не форвардить весь поток банка. Неизвестные сообщения остаются на устройстве.
3. На свой сервер — TLS с проверкой сертификата, LAN/VPN или собственный защищённый адрес, без обязательного облачного посредника. Отдельный от сессии пользователя отзывной токен устройства, ограниченный созданием входящих черновиков одной семьи. Если инструмент умеет HMAC — подписывать тело с временем и nonce; иначе bearer + event ID и защита от повторов. Секрет не в URL.
4. Пример конверта: `version, device_id, event_id, bank_hint, channel, sender_or_package, captured_at, text`. Очередь на телефоне, повторы с backoff, сервер отвечает после долговечной записи; лимит тела и частоты. Токен сам определяет семью, присланный `household_id` не является правом доступа.
5. Идемпотентность по устройству/event ID. Повтор push после обновления и SMS-дубль сопоставлять как кандидаты; одинаковые покупки не удалять по одному хешу текста. Первоначально все события — **черновики с низкой уверенностью**, сверяемые с выпиской.

**[В] Надёжность средняя/низкая:** push не гарантирует доставку, текст может быть скрыт, телефон офлайн, разрешение отозвано; уведомление часто отражает авторизацию, а не окончательную проводку. Нет полной истории, MCC, достоверного банковского ID и кредитного графика. Остаток «доступно» может включать лимит/холды. Такой канал удобен для быстрого черновика, но не для окончательного баланса.

## 6. Чеки ФНС и QR

**[П]** «Проверка чеков» ФНС позволяет сканировать QR либо вводить реквизиты: дату/время, сумму, ФН, ФД и ФП. **[В]** QR удобно читать локально; он содержит идентификаторы чека и итог, но не полную номенклатуру, банковский счёт, кредит или весь поток операций. [ФНС о приложении](https://www.nalog.gov.ru/rn01/news/activities_fts/16416287/).

**[П]** У официального «Открытого API проверки чека ККТ» внешний пользователь — организация/ИП, прошедшие регистрацию. Нужна заявка и мастер-токен; его нельзя передавать третьим лицам. Условия ограничивают цели получением/проверкой чека и гражданским контролем, а сервис описан как проверка факта расчёта/фискального признака. **[В]** Нельзя обещать семье анонимный API товарных позиций или встраивать общий мастер-токен в self-hosted дистрибутив. [Условия ФНС, версия 07.04.2022](https://kkt-online.nalog.ru/ap-description/).

**[В] Рекомендация:** локальная регистрация QR/прикрепление электронного чека, ручной ввод или импорт предоставленных пользователем данных. Автоматическое получение состава чека — отдельная задача с проверкой разрешённого канала и условий; reverse-engineered API мобильного приложения не считать официальным. Покупку из чека сопоставлять с банковской по сумме, времени и продавцу с подтверждением пользователя, иначе возникнут два расхода. Не все платежи имеют кассовый чек; чек бывает за наличные, возврат, аванс или смешанную оплату.

## 7. Скрейпинг ЛК и сторонние сервисы

### 7.1 Скрейпинг: оценить, но не делать

**[В]** Технически возможны автоматизация браузера, reverse engineering запросов мобильного приложения и промежуточная сессия. Но это нестабильные интерфейсы: SMS/2FA, антибот, CAPTCHA, изменение страниц и схем, истечение cookies, подтверждения новых устройств. Сессия обычно даёт больше полномочий, чем чтение; ошибка автоматизации может стать действием со счётом. Нулевой бюджет не покрывает сопровождение трёх банков и разбор инцидентов.

**[П]** Банк предупреждает не передавать пароли и коды подтверждения. ЦБ разъясняет, что нарушение порядка использования электронного средства платежа, повлекшее операцию без согласия, имеет значение для возмещения. **[В]** Передача банковских credentials стороннему сервису создаёт договорный риск и осложняет спор при краже. Нельзя утверждать, что любой личный скрипт автоматически преступен или что возврат всегда исключён: важны договор, обстоятельства и причинная связь. [Т-Банк о безопасности](https://www.tbank.ru/finance/blog/kids-safety/), [разъяснения ЦБ по ст. 9 161-ФЗ](https://www.cbr.ru/explan/Psystem/).

**[Н]** Полный актуальный договорный запрет конкретного вида локальной автоматизации для всех трёх банков не установлен. **[В]** Это не разрешение банка на скрейпинг. Перед коммерческим внедрением потребовались бы проверка актуальных ДБО/ToS каждого банка и письменные условия интеграции. Рекомендация BestBudget — отказаться от скрейпинга, не хранить банковские пароли, cookies и OTP; использовать файлы, уведомления и одобренные API при появлении доступа.

## 8. 152-ФЗ и ответственность за данные

**[П-ист]** Официальное разъяснение прокуратуры связывает конфиденциальность счетов/операций со ст. 857 ГК РФ и ст. 26 закона № 395-1 «О банках и банковской деятельности». Документ 2017 года не используется здесь как полный актуальный перечень исключений из банковской тайны. **[В]** Право владельца получить свою выписку не тождественно обязанности банка подключить произвольный сервер к API; для передачи третьей стороне нужны правовое основание и банковский механизм доступа. [Разъяснение на сайте прокуратуры](https://epp.genproc.gov.ru/ru/proc_46/activity/legal-education/explain/e437952/).

**[П]** Статья 1 ч. 2 п. 1 152-ФЗ исключает обработку физлицами исключительно для личных и семейных нужд, если не нарушены права субъектов. Для операторов вне этого исключения существенны основания обработки, конфиденциальность, защита, локализация при сборе данных граждан РФ и уведомление об обработке (ст. 6, 7, 18 ч. 5, 19, 22; применимость определяется сценарием). [Текст закона на сайте Минтруда, включает изменения 2025 года](https://mintrud.gov.ru/docs/laws/130).

**[В]** Семейный сервер с добровольным вводом собственных данных — наиболее близкий нашему исключению сценарий. Оно не разрешает нарушать права получателей переводов/других членов семьи, не отменяет условия ДБО и не даёт доступа к API. Разработчик, который только распространяет ПО и не получает выписки, отличается от оператора общего облака/аналитики. Общий relay, техподдержка с загрузкой выписок или телеметрия с описаниями операций могут изменить оценку; не считать семейное исключение универсальным для них.

**[В] Для всех каналов:** данные остаются у семьи; минимальные права, шифрование секретов и резервных копий, доступ только к своей семье, отсутствие сумм/описаний/полных номеров в обычных логах. Пользователь управляет сроком хранения оригиналов и удалением; для парсерных fixtures используются только синтетика или явно разрешённые, действительно обезличенные образцы. При утечке нужны отзыв устройства/почтового токена/согласия и понятный журнал действий. Нельзя обещать «нулевую ответственность», потому что сервер домашний.

## 10. План для BestBudget и общая архитектура импорта

### 10.1 Сейчас: 0–2 месяца

1. **[В] Получить образцы и зафиксировать границы поддержки** (1–2 дня работы без времени ожидания). По каждому банку — обычная выписка, движения между своими счетами, кредитный документ. Сохранить сведения о пути выгрузки и версии интерфейса, не реальные данные. Неподтверждённый нативный формат не включать в список «поддерживается».
2. **[В] Сделать общий импорт CSV с мастером колонок и предпросмотром** (5–8 дней): счёт, дата, валюта, приход/расход, описание; ручная привязка, проверка сумм/повторов, единый атомарный commit и отмена партии. На этой базе можно работать независимо от банковского API.
3. **[В] Добавлять адаптеры по подтверждённым файлам**, начиная с таблиц Т-Банка и Альфы, если они доступны у владельца; затем конкретный PDF Сбера. Не выбирать сложность по предположению, что «Excel» обязательно XLSX.
4. **[В] Кредиты пока вводить вручную**: на дату сверки долг, ближайший платёж, дата, отдельно текущий график. В MVP можно прикрепить документ без распознавания; будущий импорт графика не создаёт фактические расходы.

### 10.2 Затем: 2–6 месяцев

**[В]** После устойчивого файлового пути добавить либо IMAP, либо Android-черновики по запросу пользователей. Это два независимых адаптера к одному входному конвейеру. Выбирать по реально доступной бесплатной доставке, не по обещанной. Чеки — обогащение уже существующей покупки; отдельная приёмка, чтобы не дублировать расходы. Не вводить обязательную очередь/Redis для первого файлового импорта: текущий один сервис + PostgreSQL достаточен при ограниченных партиях.

### 10.3 Повторная проверка через 6–12 месяцев: 23.04–23.10.2027

**[В]** Условие начала API-разработки — не просто новая дата в календаре. Проверить: опубликован ли обязательный закон/акт с датой и перечнем банков; кто допускается как СПУ; где реестр и процедура; допускаются ли физлица/self-hosted клиенты; платность, сертификаты/ИБ; банковские production endpoints, глубина истории и отдельная схема кредитов. Сделать матрицу источников заново, используя действующие редакции.

**[В]** Если появится бесплатный одобренный путь — ограниченный read-only прототип одного банка с владельцем: выдача/отзыв согласия, обновление токенов, пагинация, повторные запросы и сверка выписки. При платной институциональной модели сохранить файловый путь. Для кредитов отдельный gate: наличие проверенных данных основного долга и актуального расписания; баланс/лимит таким gate не является.

### 10.4 Контракт конвейера, общий для файлов, почты, уведомлений и API

Все ниже — **[В] предлагаемая архитектура**, без изменения кода в этом PR. Текущие ограничения взяты из [архитектуры репозитория](../architecture.md): деньги в копейках, день в часовом поясе семьи, перевод — одна операция с двумя счетами, нет валютной конвертации и полноценной модели кредитов.

```text
Файл / IMAP / Android / одобренный API
  → приём и идентичность источника
  → распознавание профиля + сохранение происхождения
  → нормализация во входящие строки
  → сопоставление счетов, кандидаты дублей/переводов/категорий
  → предпросмотр ошибок и итогов
  → подтверждение пользователя
  → атомарная запись через сервис операций + аудит
```

- **Происхождение:** партия (`source`, версия парсера, хеш исходного файла, период, статус), входящие строки (исходная позиция, нормализованные значения, уверенность), связь строки с итоговой операцией. Это новые сущности, не существующие таблицы. Оригинал хранить по настройке семьи; raw-текст никогда не выводить в общие логи.
- **Идемпотентность:** при наличии надёжного банковского ID — уникальность в области `household + connection + bank_account + external_id`. Файл — собственный SHA-256 для отсечения точного повтора. Без банковского ID — fingerprint из привязанного счёта, валюты, подписанной суммы, точной исходной даты/времени и нормализованного описания, плюс дополнительный банковский reference при наличии. **Не делать hash(date, amount) уникальным ключом:** две одинаковые покупки законны. Для перекрывающихся файлов — сверка мультимножеств совпадений и подтверждение спорных строк; file hash не решает пересечение периодов. Ключи scoped по семье и источнику; SMS-хеш не банковский ID.
- **Сопоставление счетов:** стабильный банковский account ID/номер → выбранный `financial_account`. Последние четыре цифры карты — только подсказка; они могут совпадать, карта перевыпускается, несколько карт ведут к одному счёту. Не создавать новый счёт автоматически из каждой карты; начальный остаток задаётся на дату до импортируемого периода, чтобы не удвоить текущий баланс.
- **Суммы и дата:** оригинальные валюта/сумма операции и валюта/сумма списания отдельно. В текущую RUB-книгу писать сумму проводки в RUB; неподдерживаемую валюту отправлять на проверку, не пересчитывать по сегодняшнему курсу. Сохранять обе даты и время источника во входящей записи, даже если итоговая модель хранит только день. `pending`/холд не считать завершённой проводкой.
- **Категории:** локальные правила по нормализованному описанию, merchant и MCC при наличии; банковскую категорию хранить как метаданные. Пользовательские правила имеют приоритет, версия правила видна в предпросмотре. MCC — строка из четырёх цифр, может отсутствовать; он не описывает состав корзины. Возвраты и комиссии не угадывать только по знаку.
- **Свои переводы:** кандидаты по явным реквизитам своих счетов, одинаковой валюте/сумме и противоположным направлениям в окне дат; неоднозначность требует подтверждения. Две строки выписки превращаются в одну `transfer` с двумя ссылками происхождения. Если вторая сторона придёт позже, присоединить её к переводу, а не добавить доход. Комиссия — отдельный расход. Перевод другому человеку — не «свой» по одному слову СБП.
- **Кредиты:** погашение кредитки — перевод на счёт с долгом; покупки по ней — расходы один раз. Для обычного кредита проектировать отдельные `loan_snapshot`/`schedule_version`/состав платежа. Нельзя повторно записать весь платёж расходом после учёта тела долга. График идёт в план, выписка — в факт, сопоставление с существующим planned-платежом сохраняет одну фактическую операцию. Ввод этих сущностей — отдельная разработка.
- **Предпросмотр:** выбор счёта и периода, подтверждение направления, число строк, приходы/расходы и остатки, кандидаты дублей и переводов, отдельно отклонённые/непонятные строки; пользователь может исправить сопоставление. При несходящейся контрольной сумме нельзя молча завершать импорт.
- **Сохранение и восстановление:** транзакция БД, уникальные ограничения идемпотентности против гонок, проверка прав через семейный контекст/сервис операций, аудит партии. Повтор после тайм-аута возвращает уже записанный результат. Отмена партии не удаляет изменённые пользователем или связанные с другой партией записи без отдельного разрешения.

**[В] Критерии приёмки будущей реализации:** повтор и пересечение выгрузок не удваивают операции; две одинаковые покупки сохраняются; перевод/погашение кредитки не удваивает расход; pending/отмена/возврат различаются; обороты и остатки сходятся; неизвестный формат даёт объяснимый отказ; другая семья не видит входящие данные; оригинал/секреты не попадают в логи. Синтетические примеры проверяют логику, а банковский профиль принимается только после локальной проверки реальной обезличенной выгрузки.
