# Выписки банков РФ: спецификация и границы подтверждения

Дата проверки: **23.10.2026**. Банки: Сбер, Т-Банк, Альфа-Банк РФ; клиенты — физлица. Документ предназначен для будущего автора парсеров. Код, парсеры и реальные банковские fixtures этим исследованием не создаются.

**Ни одного исходного файла владельца нет. Точные нативные форматы 2026 года не установлены достаточно для production-парсера.** Ниже дан проверяемый контракт общего импорта, исторический кандидат CSV Т-Банка и задания по подтверждению банковских профилей. Выдуманные колонки не объявляются банковским форматом. Все строки примеров синтетические и не содержат реальных ФИО, счетов, карт, чеков или операций.

Метки: **[П]** — первоисточник; **[П-ист]** — исторический первоисточник, текущий интерфейс не подтверждён; **[С]** — вторичное свидетельство; **[Н]** — неизвестно; **[В]** — предлагаемый контракт/правило BestBudget. Все ссылки проверялись 23.10.2026. Состояние API, правовые ограничения и сравнение каналов — в [основном отчёте](bank-integrations-ru.md).

## 2. Общий контракт импортера

Все требования этого раздела — **[В]**, не описание банковской схемы и не готовая функциональность BestBudget.

### 2.1 Входной результат любого адаптера

| Поле входящей строки | Тип / обязательность | Правило |
|---|---|---|
| `source`, `profile_version`, `batch_id`, `row_locator` | строки, обязательно | Банк/канал, версия парсера, партия, строка/страница/координаты; нужны для диагностики |
| `account_hint` | строка или null | ID счёта/маска/ручная привязка; последние 4 цифры не являются глобальным ID |
| `external_id` | строка или null | Только документированный стабильный банковский идентификатор; не номер строки или код авторизации |
| `operation_at_raw`, `booking_date_raw` | строки или null | Сохранять обе исходные даты, не затирать одну другой |
| `effective_date` | `YYYY-MM-DD`, обязательно для готовой строки | Для завершённого движения по счёту приоритет дате проводки; политику показать в предпросмотре |
| `amount_minor_signed` | целое, обязательно | Сумма движения **по выбранному счёту**: плюс приход, минус расход; никакого float |
| `currency` | строка, обязательно | ISO-код валюты движения по счёту; не угадывать по символу без профиля |
| `original_amount_minor_signed`, `original_currency` | опционально | Исходная сумма покупки до конвертации; не вторая транзакция |
| `status` | `posted / pending / rejected / unknown` | Неизвестный статус требует проверки; `pending` не записывать сразу в факт |
| `description_raw`, `description_normalized` | строки | Исходник для пользователя, нормализация для поиска; не в обычные логи |
| `mcc` | строка или null | Ровно четыре цифры при наличии; `0000` не подставлять вместо неизвестного |
| `bank_category`, `card_hint`, `counterparty_hint` | опционально | Подсказки, не готовая категория и не доказательство своего перевода |
| `balance_after_minor` | целое или null | Только остаток по счёту с понятной семантикой, не «доступно с лимитом» |
| `confidence`, `warnings` | оценка и список | Неразрешённый знак, неоднозначная дата, неизвестный счёт, неподдерживаемая валюта |

Если не хватает обязательного поля, строка остаётся в предпросмотре с ошибкой. `external_id`, MCC, категория и остаток не обязательны для файлового импорта. Пустое значение и числовой ноль различаются.

### 2.2 Чтение CSV и Excel

- Определять файл по содержимому, а не только имени. CSV — текст, XLSX — ZIP/OOXML, старый XLS — отдельный бинарный формат; не пытаться разобрать XLS CSV-парсером. Не исполнять макросы/формулы, не запрашивать внешние ссылки.
- CSV сначала декодировать строго: BOM UTF-8/UTF-16; без BOM пробовать строгий UTF-8, затем пользовательский выбор Windows-1251 и других допустимых вариантов. То, что CP1251 декодирует почти любые байты, не делает результат верным. Нужен предпросмотр заголовков/текста; не сохранять повреждённые символы молча.
- Кандидаты разделителя `;`, `,`, табуляция — только внутри полноценного CSV-парсера с кавычками, удвоенными `"` и переносами внутри поля. Не применять `split(';')`. Автоопределение проверяет одинаковую ширину и известные заголовки; неоднозначность решает пользователь.
- Для идентификации заголовков убрать BOM и крайние пробелы, нормализовать NBSP и регистр; перестановка колонок допускается. Словарь aliases должен быть версионирован. Не переводить автоматически разные заголовки в одно поле, если их смысл различается.
- Даты разбирать по конкретному профилю: `DD.MM.YYYY`, при наличии времени — отдельный заданный шаблон. `01/02/2026` без локали неоднозначна, двухзначный год требует правила пользователя. Excel numeric date — с учётом системы 1900/1904 конкретной книги; не вычислять дату из серийного числа без типа ячейки.
- Деньги: убрать разделители тысяч (обычный/NBSP/узкий пробел), нормализовать знак `−`, использовать десятичную арифметику и проверку копеек. `1 234,56` → `123456`; `-1 234,56` → `-123456`. Точка и запятая не удаляются одновременно «на всякий случай». Более двух знаков для RUB — ошибка либо явное согласованное округление, не silent truncation.
- Знак/направление задаётся профилем или мастером: подписанная сумма, две колонки приход/расход либо направление + модуль. У двухколоночной строки оба ненулевых значения — ошибка. Положительная сумма не обязательно приход в неизвестной банковской форме.
- Для текущей модели RUB использовать сумму проводки по RUB-счёту. Исходные USD/EUR сохранить как метаданные. Без RUB-суммы не конвертировать и не принимать в рублёвую книгу автоматически.

### 2.3 Универсальный CSV BestBudget v1 — наш предлагаемый формат

Это **наш** контракт для ручного сопоставления/конвертации, не банковская выгрузка. Можно реализовать, не ожидая подтверждения нативных форматов. Кодировка UTF-8, допустим BOM; разделитель `;`, CRLF или LF; даты ISO; суммы в основных единицах с точкой и необязательным ведущим `-`; валюта обязательна. Кавычки CSV стандартные.

Обязательные колонки: `account`, `date`, `amount`, `currency`, `description`. Остальные опциональны; `status` по умолчанию `posted` только для **этого** явно выбранного профиля. `date` — согласованный пользователем день движения по счёту.

```csv
account;date;amount;currency;description;external_id;status;mcc;kind_hint
DEMO_DEBIT_A;2026-10-20;-450.00;RUB;MAGAZIN PRIMER;;posted;5411;purchase
DEMO_DEBIT_A;2026-10-21;-2000.00;RUB;Перевод на собственный счёт;;posted;;own_transfer_candidate
DEMO_SAVINGS_A;2026-10-21;2000.00;RUB;Перевод с собственного счёта;;posted;;own_transfer_candidate
DEMO_DEBIT_A;2026-10-22;50.00;RUB;Рублёвый кэшбэк;;posted;;cashback
DEMO_CREDIT_A;2026-10-22;-600.00;RUB;Покупка по кредитной карте;;posted;5812;purchase
DEMO_DEBIT_A;2026-10-23;-600.00;RUB;Погашение своей кредитной карты;;posted;;own_transfer_candidate
DEMO_CREDIT_A;2026-10-23;600.00;RUB;Погашение с собственного счёта;;posted;;own_transfer_candidate
```

Ожидается 7 входящих строк → 5 итоговых операций: 2 покупки, 2 перевода с двумя сторонами, 1 рублёвое начисление. Расходы от покупок — 1050 ₽. Категория учёта рублёвого кэшбэка выбирается пользователем. `kind_hint` — подсказка для предпросмотра; она не разрешает автоматически объединять чужие счета. Ожидаемая сумма всех движений — −1000 ₽; свои переводы в ней взаимно погашаются.

## 3. Т-Банк: кандидат CSV

### 3.1 Получение и степень достоверности

**[П]** ЛК на компьютере → «Операции» → период/продукты → «Поделиться» → формат. Справка подтверждает экспорт, но не его полный диалект. [Документация банка](https://www.tbank.ru/bank/help/debit-cards/tinkoff-black/get-statement/reference/).

**[С]** Ниже профиль `tbank-csv-legacy-candidate`, основанный на сообщении автора выгрузки 2018 года. Это исходное свидетельство пользователя файла, **не первоисточник банковской спецификации**. Установлены видимые заголовки, `;`, кавычки, формат даты/десятичной запятой в примере; байтовая кодировка и актуальность не установлены. [Сообщение и пример](https://github.com/moneymanagerex/moneymanagerex/issues/1859).

### 3.2 Сопоставление колонок кандидата

Следующие действия — **[В] гипотезы адаптера, подлежащие проверке** на образце; нельзя автоматически узнавать формат только по названию банка.

| Исторический заголовок | Предполагаемое значение | Обработка |
|---|---|---|
| `Дата операции` | Время события | Сохранить `DD.MM.YYYY HH:mm:ss`; часовой пояс в строке отсутствует |
| `Дата платежа` | Дата проводки | Кандидат `effective_date`, если не пуста и статус подтверждён |
| `Номер карты` | Маска карты | Подсказка; для некарточной операции может отсутствовать |
| `Статус` | Результат | В историческом примере `OK`; остальные и окончательность `OK` проверить |
| `Сумма операции`, `Валюта операции` | Исходная сумма | Сохранять отдельно от суммы движения по счёту |
| `Сумма платежа`, `Валюта платежа` | Сумма движения | Предпочтительный кандидат для изменения баланса |
| `Кэшбэк` | Неустановленная семантика | Метаданные; не создавать доход из каждой покупки |
| `Категория` | Категория банка | Только предложение категоризации |
| `MCC` | Код торговца | Nullable, строка из четырёх цифр при наличии |
| `Описание` | Назначение/торговец | Сохранять оригинал; нормализовать отдельно |
| `Бонусы (включая кэшбэк)` | Неустановленные единицы/момент начисления | Метаданные, не прибавлять к балансу |

**[Н]** В более новых выгрузках могут быть округления/дополнительные колонки, другие заголовки и статусы. Их имена, обязательность и семантика не установлены; не добавлять вымышленные поля в детектор. «Сумма покупки» и «списание с округлением» могут различаться — нужен отдельный пример и контроль по остатку.

### 3.3 Синтетические строки кандидата

Это **учебный файл, созданный для иллюстрации гипотез**, а не воспроизведённая выписка банка. Текущие даты не означают, что такой шаблон проверен в 2026 году. Выбран UTF-8 без BOM для примера; это не утверждение о банковской кодировке.

```csv
"Дата операции";"Дата платежа";"Номер карты";"Статус";"Сумма операции";"Валюта операции";"Сумма платежа";"Валюта платежа";"Кэшбэк";"Категория";"MCC";"Описание";"Бонусы (включая кэшбэк)"
"20.10.2026 18:20:00";"21.10.2026";"*1234";"OK";"-450,00";"RUB";"-450,00";"RUB";"";"Супермаркеты";"5411";"MAGAZIN PRIMER";"0,00"
"21.10.2026 09:00:00";"21.10.2026";"";"OK";"2000,00";"RUB";"2000,00";"RUB";"";"Пополнения";"";"Пополнение собственного счёта";"0,00"
"22.10.2026 12:00:00";"23.10.2026";"*1234";"OK";"450,00";"RUB";"450,00";"RUB";"";"Прочие";"5411";"Возврат MAGAZIN PRIMER";"0,00"
```

Предполагаемые результаты после подтверждения профиля: `-45000`, `+200000`, `+45000` копеек; даты движения 21, 21, 23 октября; MCC покупки и возврата `5411`, у пополнения null. Возврат — кандидат связи с покупкой, не новый заработок. В строках нет стабильного внешнего ID и номера банковского счёта: пользователь должен привязать счёт; для выгрузки сразу нескольких продуктов одной маски недостаточно.

### 3.4 Что проверять до выпуска

- Исходные байты CSV, BOM/кодировку, разделитель, порядок/названия полей, число строк, кавычки в описании.
- Дебет/кредит и sign на реальном приходе, покупке, возврате и отмене; отсутствие даты проводки и все статусы. `FAILED`/`PENDING` не считать действительными банковскими значениями, пока они не наблюдались.
- Две одинаковые покупки в одну секунду/день; межсчётный перевод; пустую маску карты; кредитную карту и счёт без карты.
- Две валюты: по балансу проводить сумму платежа, не обе суммы. Если есть отдельные округления/комиссии — выяснить, входят ли они в сумму или идут строками.
- Кэшбэк в строках покупок против фактического отдельного рублёвого зачисления; бонусные единицы против рублей.
- Месячный PDF/письмо не подменяет этот профиль CSV. **[П]** Банк отдельно описывает краткую месячную выписку и подробную справку с движением. [Состав документов](https://www.tbank.ru/bank/help/debit-cards/tinkoff-black/get-statement/account-statement/).

**Статус адаптера: экспериментальный кандидат; заблокирован для автоматической записи до получения образца 2026 года.** При несовпадении схемы — универсальный мастер колонок, а не частично успешный тихий импорт.

## 4. Сбер: профиль PDF ещё не установлен

### 4.2 Колонки и физическое представление

**[Н]** Точные заголовки, расположение, знак приходов/расходов, уникальные коды, даты операции/обработки, MCC и представление остатка в розничном PDF 2026 не установлены. Нельзя объявить CSV-кодировку или разделитель для PDF: это контейнер с текстовыми блоками и шрифтами, не текстовая таблица.

**[В]** Из образца нужно установить: название/версию документа, границы таблицы; номер/валюту счёта; период; начальный/конечный остаток; порядок сортировки; колонки даты события/проводки, описания, списания/зачисления/подписанной суммы, остатка; наличие карточной маски/референса. Отдельно проверить платёжный счёт, дебетовую карту, вклад/накопительный счёт и кредитку. До этого названия полей ниже — **наши нормализованные поля, не реальные заголовки PDF**.

Синтетический ожидаемый результат будущего PDF-парсера:

```csv
account_hint;effective_date;amount_minor_signed;currency;description_raw;mcc
DEMO_SBER_ACCOUNT;2026-10-20;-45000;RUB;MAGAZIN PRIMER;
DEMO_SBER_ACCOUNT;2026-10-21;200000;RUB;Пополнение собственного счёта;
```

### 4.3 Алгоритм после получения образца

Все пункты — **[В]**:

1. Различать text PDF, скан и документ под паролем. Без текстового слоя/с неизвестным паролем — понятный отказ, не автоматический OCR финансовых чисел в первой версии. Не снимать ограничения незаметно для пользователя.
2. Извлекать слова с координатами; закрепить детектор версии по заголовку и структуре шапки, не по одному слову «Сбер». Смешанные продукты и неизвестную версию отклонять.
3. Восстанавливать строки с учётом переносов описания, даты на соседней строке, многостраничной таблицы, повторных шапок, итогов/сносок. Не искать все числа регулярным выражением: баланс, код операции, дата и сумма могут стоять рядом.
4. Вывести знак **из подтверждённой семантики конкретного шаблона**. Пропавший при извлечении `+`, тире или цвет не должны превращать приход в расход. Не полагаться на цвет без доступной текстовой семантики.
5. Проверить `начальный остаток + приходы − расходы = конечный остаток` для проведённых операций и согласованного периода. Если остаток/итоги недоступны, показывать отсутствие контроля, а не «сверено».
6. Не считать шестизначный код авторизации глобальным ID. Не выводить MCC из текстовой категории и не считать перевод своим без подтверждения счёта.

**Статус адаптера: schema pending; без образца реализация конкретной раскладки заблокирована.** Общий конвейер и обработку файлов можно разрабатывать независимо.

### 5.2 Контракт будущего профиля

**[Н]** Не установлены точные названия/порядок колонок Excel/CSV, различие дат, знак и валюты, формулы/значения ячеек, наличие банковского ID и MCC. Нельзя брать бизнес-форматы JSON/1С/MT940 либо выписки Альфа-Банка Беларуси как российскую розничную схему.

**[В]** После получения файла зафиксировать worksheet и строку заголовка, объединённые ячейки/служебную шапку, диапазон данных, итоги и пропуски. Для CSV — исходные байты/диалект. Для PDF — отдельный профиль координат и проверки из раздела Сбера; один и тот же код раскладки на два банка не распространять.

**[В]** Минимальные семантические поля адаптера: счёт, валюта, дата проводки или однозначная дата операции, описание, направление/сумма. При наличии — оригинальная сумма, банковская категория, MCC, остаток. Это задание на установление схемы, не список банковских колонок.

Синтетический результат нормализации (не нативный Excel/CSV Альфы):

```csv
account_hint;effective_date;amount_minor_signed;currency;description_raw;mcc
DEMO_ALFA_ACCOUNT;2026-10-20;-45000;RUB;MAGAZIN PRIMER;
DEMO_ALFA_ACCOUNT;2026-10-21;-200000;RUB;Перевод на собственный счёт;
DEMO_ALFA_ACCOUNT;2026-10-22;5000;RUB;Рублёвое начисление вознаграждения;
```

**[В]** Последнее начисление становится доходом/компенсацией только после подтверждения, что это действительно рублёвое движение по счёту. Баллы, предварительно рассчитанный кэшбэк и категория покупки не создают отдельную операцию. Списание перевода не признаётся своим без сопоставления второй стороны.

**Статус адаптеров: Excel/PDF schema pending; CSV — исторически заявленный, текущая доступность pending.** Если владелец не видит Excel/CSV, не требовать открытия бизнес-счёта; использовать PDF/ручной общий импорт.

### 6.2 Предлагаемая нормализованная схема — не банковские колонки

Все требования ниже — **[В]**.

Снимок: `loan_hint`, `product_type`, `currency`, `as_of_date`, `principal_outstanding_minor`, `accrued_interest_minor?`, `overdue_minor?`, `payoff_quote_minor?`, `payoff_quote_date?`, `next_due_date?`, `next_due_minor?`. Не подставлять `payoff_quote` в `principal_outstanding` и не считать остаток расчётного счёта долгом.

График: идентификатор договора-подсказки, дата/версия документа, признак актуальности, номер платежа, срок, общий платёж, тело, проценты, комиссии/страхование при наличии, остаток тела после платежа **только если указан**. Отсутствующие компоненты — null. Новая версия графика не создаёт дубли будущих расходов. Внешний номер договора может быть ПД и в fixtures заменяется псевдонимом.

Учебный CSV графика BestBudget (UTF-8, `;`, ISO-даты, копейки целыми; **не выдаваемый банками формат**):

```csv
loan_hint;schedule_version;due_date;payment_minor;principal_minor;interest_minor;fees_minor;principal_after_minor
DEMO_LOAN_A;demo-v1;2026-11-15;120000;100000;20000;0;200000
DEMO_LOAN_A;demo-v1;2026-12-15;120000;105000;15000;0;95000
DEMO_LOAN_A;demo-v1;2027-01-15;100000;95000;5000;0;0
```

Начальный основной долг этой синтетики — 300000 копеек, сумма тела — 300000, процентов — 40000, всех платежей — 340000. Для каждой строки `payment = principal + interest + fees`; не применять эту проверку, если документ не раскрывает все компоненты. План не отражается в фактическом балансе до банковской проводки. Для кредитной карты фиксированный график не выводится из минимального платежа.

## 7. Как получить образцы и снять неопределённость

Это **[В] протокол следующего шага**, а не запрос доступа к банкам в текущей задаче. Владелец сам выгружает документы; агенту не нужны пароль банка, QR входа или SMS-код.

1. По каждому банку выгрузить короткий период с покупкой, приходом, возвратом и переводом между своими счетами; предпочтительнее один законченный месяц и отдельный файл с пересекающимся периодом. Сохранить именно исходную выгрузку без пересохранения через Excel, чтобы не потерять диалект/кодировку.
2. Записать без персональных данных: банк РФ, продукт, дата выгрузки, ОС/версия приложения или веб-ЛК, путь меню, выбранный тип документа, предложенные форматы, период, наличие фильтра по счёту/карте. Проверять, не смешаны ли несколько счетов в файле.
3. Табличный файл обезличить **локально**: убрать/заменить ФИО, полные номера/IBAN, телефоны, адреса, договоры, назначения с ПД, ID людей и платёжные ссылки. Сохранить число и имена колонок, типы ячеек, знаки, формат дат/сумм и пустоты. Маски/ID заменить согласованно, чтобы пары переводов и повторные файлы оставались сопоставимыми. Не использовать правдоподобные действующие реквизиты.
4. Для PDF простого чёрного прямоугольника недостаточно: исходный текст может остаться внутри. Применить настоящую редактирующую очистку, удалить метаданные, вложения, активные ссылки и QR проверки документа (он может открывать исходные данные). Локально проверить копирование/извлечение текста и изображения. Растрирование удалит текстовый слой и испортит образец для text-PDF-парсера — тогда безопаснее локально создать синтетическую реплику структуры и сверить её на оригинале без передачи оригинала.
5. Суммы/даты при необходимости заменить согласованно, сохраняя арифметику остатков/графика. Не передавать оригиналы через публичные онлайн-конвертеры. Исходники остаются у владельца; в репозиторий не попадёт файл только потому, что он «замаскирован».
6. Кредиты запросить отдельно: актуальный график и снимок основного долга на дату, тип продукта; желательно две обезличенные версии до/после досрочного платежа. Выписка счёта обслуживания не заменяет эти документы.
7. Уведомления собирать добровольно на устройстве для каждого типа события; удалить OTP/логины целиком, маски заменить. Известные банковские sender/package и тексты хранить только в локальном профиле; синтетическую fixture сделать отдельно. Синтетика не подтверждает реальную доставку.

Результат подтверждения профиля: manifest с банком/каналом/версией, источником и датой; SHA-256 **публичной синтетической fixture**, ожидаемое число операций и контрольные суммы; точные заголовки/диалект, политика дат/знаков/статусов, список ограничений. Хеши персональных исходников без необходимости не публиковать. Локальная проверка на настоящем файле может быть зафиксирована без самого файла.

## 8. Обязательные подводные камни и проверки реализации

Все пункты — **[В]**. Это будущие критерии проверки, тесты в данном PR не создавались.

| Случай | Ожидаемое поведение |
|---|---|
| Один файл дважды / повтор сохранения после тайм-аута | Одна партия и прежний результат, без повторной записи |
| Два файла с пересечением периода | Сопоставление строк с учётом кратности, спорные совпадения в предпросмотр |
| Две одинаковые покупки | Обе сохраняются; дата+сумма+описание не уникальный банковский ID |
| Приход без явного `+` / отдельные колонки | Направление из профиля/мастера, не из догадки |
| `1 234,56`, `−450,00`, `0,00`, пустое поле | Корректные целые копейки; ноль и null различаются |
| Кавычки, `;`, перенос строки в описании | Одно поле/одна операция, полноценный CSV-парсер |
| UTF-8 BOM и CP1251 | Корректная кириллица или явный выбор, без тихой замены символов |
| Покупка и проводка в разные дни | Обе даты сохранены; политика итогового дня объяснена |
| Холд, неуспех, отмена, частичный/полный возврат | Отдельные состояния; отменённый холд не расход, возврат не обычная зарплата |
| Несколько карт одного счёта / одинаковая маска разных счетов | Ручное разрешение, не новый счёт на каждую карту |
| Свой перевод в двух выписках / вторая сторона позже | Один перевод с двумя связями происхождения; без лишних дохода/расхода |
| Свой перевод с комиссией / перевод чужому человеку | Комиссия отдельно; направление и принадлежность подтверждены |
| Погашение кредитки | Перевод на счёт долга; покупки уже учтены расходами |
| Кэшбэк рублями, бонусами и предварительное начисление | Денежная операция только для фактического движения; единицы не смешиваются |
| MCC отсутствует / категория известна | MCC=null; категория/описание используются как подсказки |
| Конвертация и округления | Проверка суммы движения по счёту; не двойной учёт исходной валюты |
| PDF с переносом на страницу / повторной шапкой / итогами | Описания объединены, шапки/итоги не стали операциями |
| PDF неизвестной версии, скан или под паролем | Объяснимый отказ, исходные данные не теряются, нет «успешно 0 операций» |
| Несходящиеся остатки/обороты | Остановка автоматического сохранения и объяснение расхождения |
| SMS/push, затем выписка той же покупки | Кандидат сверки черновика; разные источники не создают два факта |
| Новый график после досрочки | Новая версия плана, не дубли будущих платежей и не изменение старого факта |
| Две семьи / токен устройства другой семьи | Изоляция до чтения/записи, включая входящие строки и оригиналы |

Готовность конкретного профиля означает проверку не только синтетики, но и исходной банковской структуры с согласия владельца. Пока такой приёмки нет, показывать «универсальный импорт с сопоставлением» или «экспериментальный профиль», а не «поддержка банка 2026».
